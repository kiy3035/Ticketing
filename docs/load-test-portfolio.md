# 부하 테스트 — 병목 진단 & 대기열 최적화

## 개요

| 항목 | 내용 |
|------|------|
| **도구** | k6 |
| **시나리오** | `queue-flow.js` — 대기열 진입(POST /api/queue/enter) → 순번 폴링(GET /api/queue/status) → 입장 허용 확인 |
| **관측** | Prometheus + Grafana 6패널 (RPS · HTTP p95 · DB active/pending · 대기열 인원 · JVM threads) |
| **실행 방식** | 설정 변경 시 앱 재기동. Run 2·3 전에 **Redis 전체 키 삭제(cold)**. 중앙값 기준 분석 |
| **Run 1 특성** | 설정 변경 → 앱 재기동 → **JVM cold start** (JIT 미적용). Redis도 cold. 모든 실험의 Run 1이 느린 일관된 원인 |
| **Run 2·3 특성** | JVM warm (Run 1에서 JIT 적용됨) + Redis cold (전체 삭제 후 재시작). Run 간 유일한 차이는 JVM 상태 |

## Phase 1 — DB 병목 진단

**목적**: `GET /api/queue/status` 폴링이 매 요청마다 DB를 3회 조회(`countByConcertId`, `countByStatus`, `findSeatIds`)하는 구조에서, DB 커넥션 풀 크기와 Virtual Thread가 성능에 미치는 영향을 측정한다.

**고정 조건**: 캐시 미적용, VU=800, `K6_QUEUE_POLL_SLEEP_SEC=0.005`

---

### 실험 1 — pool=10 (기준선)

**가설**: DB 커넥션 풀이 10개밖에 없으면 VU 800에서 빠르게 포화될 것이다.

**조건**: `spring.datasource.hikari.maximum-pool-size=10`, Virtual Thread 미적용

#### 3회 결과

| 회차 | p(95) | p(90) | avg | 에러율 | RPS |
|------|-------|-------|-----|--------|-----|
| 1회 | 4.52 s | 3.67 s | 3.21 s | **0.08%** | 189.8/s |
| 2회 | 1.93 s | 1.76 s | 1.45 s | 0.00% | 408.3/s |
| 3회 | 1.86 s | 1.68 s | 1.24 s | 0.00% | 466.6/s |
| **중앙값** | **1.93 s** | **1.76 s** | **1.45 s** | **0.00%** | **~408/s** |

> 대표 결과: 2회차 (JVM warm-up 이후 안정화된 수치)

![pool=10 Grafana 2회차](../portfolio/1.%20캐시전_poolsize10_batchsize50_vu800_0.005/2회차.png)
*DB active=10 포화 + pending 적체가 선명하게 나타남*

#### 해석

**1회차 이상치 원인 — JVM Cold Start**

설정 적용을 위해 앱을 재기동했기 때문에 Run 1은 JIT 컴파일이 전혀 안 된 인터프리터 모드로 시작된다. Redis는 Run 2·3 전에도 전체 삭제하므로 모든 Run이 동일하게 Redis cold다. Run 1이 느린 이유는 Redis 상태가 아니라 **JVM cold start**가 유일한 원인이다. Run 2부터 JIT가 hot path를 최적화하면서 안정화된다.

실제 운영에서도 신규 배포 직후 트래픽을 점진적으로 올리는(warm-up) 이유가 여기에 있다.

**Pool=10 포화 확인 (Grafana)**

Grafana에서 `hikaricp_connections_active`가 10에서 플랫하게 유지되고 `hikaricp_connections_pending`이 ~170까지 적체됐다. 요청이 커넥션을 얻기 위해 큐잉되면서 응답 시간이 늘어났다.

**중앙값 기준 성능**: p95=1.93s, 에러 0% — DB 풀 포화 상태에서도 에러는 거의 없으나 지연이 크다.

### 실험 2 — pool=30

**가설**: 풀을 3배로 늘리면 pending 적체가 해소되어 지연이 눈에 띄게 줄어들 것이다.

**조건**: `spring.datasource.hikari.maximum-pool-size=30`, Virtual Thread 미적용

#### 3회 결과

| 회차 | p(95) | p(90) | avg | 에러율 | RPS |
|------|-------|-------|-----|--------|-----|
| 1회 | 5.44 s | 3.57 s | 3.40 s | 0.00% | 171.8/s |
| 2회 | 1.85 s | 1.67 s | 1.52 s | 0.00% | 386.3/s |
| 3회 | 1.49 s | 1.43 s | 1.19 s | 0.00% | 468.9/s |
| **중앙값** | **1.85 s** | **1.67 s** | **1.52 s** | **0.00%** | **~386/s** |

> 대표 결과: 2회차

![pool=30 Grafana 2회차](../portfolio/2.%20캐시전_poolsize30_batchsize50_vu800_0.005/2회차.png)
*pending이 pool=10보다 줄었으나 p95·RPS 개선은 미미 — 커넥션 수가 병목이 아님을 시각적으로 확인*

#### 해석

**가설 기각 — 풀 크기가 병목이 아니다**

1회차는 앱 재기동에 따른 JVM cold start로 분석에서 제외한다(p95=5.44s).

2·3회차 중앙값 p95=1.85s로, pool=10(p95=1.93s)과 비교하면 **0.08s 단축에 그쳤다.** RPS도 386/s로 pool=10(408/s)과 큰 차이가 없다. Grafana에서 `hikaricp_connections_pending`은 ~5–100으로 pool=10(~170)보다 줄었지만, 응답 시간에는 거의 반영되지 않았다.

**원인 분석**: pending이 줄어도 성능이 나아지지 않는다는 것은 커넥션 대기가 진짜 병목이 아님을 의미한다. `GET /api/queue/status`는 DB 커넥션을 얻은 뒤에도 `countByConcertId`, `countByStatus`, `findSeatIds` **쿼리 3번을 매 폴링마다 실행**한다. VU=800이 0.005초마다 폴링하면 초당 수천 건의 쿼리가 DB로 향한다. 커넥션 풀을 늘려도 **쿼리 빈도 자체는 그대로**이므로 DB 처리 용량이 한계에 도달한 것이다.

> **결론**: 병목은 커넥션 수가 아니라 `queue/status` 폴링의 반복 DB 쿼리다. pool 크기 조정으로는 해결할 수 없다.

### 실험 3 — pool=30 + Virtual Thread

**가설**: Virtual Thread로 전환하면 I/O 대기 중 OS 스레드를 점유하지 않으므로 처리량이 개선될 것이다.

**조건**: `spring.datasource.hikari.maximum-pool-size=30`, `spring.threads.virtual.enabled=true`

#### 3회 결과

| 회차 | p(95) | p(90) | avg | 에러율 | RPS |
|------|-------|-------|-----|--------|-----|
| 1회 | 12.35 s | 4.32 s | 4.19 s | 0.00% | 144.5/s |
| 2회 | 2.06 s | 1.92 s | 1.59 s | 0.00% | 375.7/s |
| 3회 | 1.95 s | 1.76 s | 1.32 s | 0.00% | 436.2/s |
| **중앙값** | **2.06 s** | **1.92 s** | **1.59 s** | **0.00%** | **~376/s** |

> 대표 결과: 2회차 — JVM threads 패널이 핵심

![pool=30+VT Grafana 2회차](../portfolio/3.%20캐시전_poolsize30_batchsize50_VT_vu800_0.005/2회차.png)
*우측 하단 JVM threads: ~225개 → ~30개로 급감. DB active/pending 패턴은 pool=30과 동일하여 처리량 개선 없음을 함께 확인*

#### 해석

**JVM 스레드 감소는 명확, 처리량 개선은 없음**

1회차는 앱 재기동(VT 설정 활성화) + cold JVM으로 p95=12.35s. 이전 실험보다 더 나쁜 것은 VT 초기화 자체의 오버헤드가 JIT warm-up 전에 집중되기 때문이다. 2·3회차 중앙값 p95=2.06s는 pool=30(1.85s)보다 소폭 높다.

Grafana에서 `jvm_threads_live_threads`는 **~225개 → ~30개**로 급격히 감소했다. Virtual Thread로 전환 시 Tomcat 요청 스레드가 경량 가상 스레드로 교체되어 OS 스레드 소비가 크게 줄어든 것이다.

그러나 **처리량(RPS, p95)은 개선되지 않았다.** Virtual Thread는 I/O 대기 중 OS 스레드를 점유하지 않는다는 점에서 효과적이지만, DB 자체가 처리할 수 있는 쿼리 수에는 영향을 주지 못한다. 이 시나리오에서 병목은 스레드 블로킹이 아니라 **DB 서버의 쿼리 처리 한계**다.

> **결론**: VT는 JVM 스레드 절감(~225→~30)이라는 명확한 효과가 있으나, 이 시나리오에서 병목은 스레드 수가 아닌 DB 쿼리 빈도이므로 처리량 개선으로 이어지지 않는다.

### Phase 1 종합 — 병목 진단 결과

| 구성 | p(95) 중앙값 | RPS 중앙값 | 에러율 | JVM threads |
|------|------------|----------|--------|-------------|
| pool=10 | 1.93 s | ~408/s | 0% | ~225개 |
| pool=30 | 1.85 s | ~386/s | 0% | ~225개 |
| pool=30 + VT | 2.06 s | ~376/s | 0% | **~30개** |

세 실험 모두 p95 1.8–2.1s 구간에서 수렴했다. 변수를 바꿔도 응답 시간이 거의 나아지지 않는다는 것은 **측정된 세 변수(풀 크기, 스레드 모델) 모두 이 시나리오의 진짜 병목이 아님**을 뜻한다.

**진단**: `GET /api/queue/status`는 매 폴링마다 DB 쿼리 3회(`countByConcertId`, `countByStatus`, `findSeatIds`)를 실행한다. VU=800이 0.005초마다 폴링하면 초당 수천 건의 COUNT 쿼리가 DB로 향하고, 이것이 응답 지연의 근본 원인이다.

**해결 방향**: 폴링마다 DB를 치는 구조를 바꿔야 한다. 잔여석 수는 1–2초 단위의 근사값으로도 충분하므로 **Redis 캐시(TTL 2초)**로 DB 조회를 대체한다.

#### 1회차 격차 해설

이 실험의 Run 1은 **서버를 하루 재기동 후 완전한 cold start**로 진행됐다(설정 변경이 아닌 캐시 적용 효과만 검증하는 별도 측정). Run 2·3은 Redis 전체 삭제 후 재실행. 즉 Redis는 모든 Run에서 동일하게 cold이고, Run 1이 느린 유일한 이유는 **JVM cold start**다.

주목할 점: JVM cold + Redis cold 상태인 Run 1(1.51s)이 Phase 1의 JVM warm + 캐시 없는 Run 2(2.06s)보다 **이미 빠르다**. 캐시는 JVM이 완전히 차갑더라도 효과를 발휘한다는 것을 의미한다.

> **결론**: 캐시 적용으로 p95 **2.06s → 444ms (78% 감소)**, RPS **376 → 834/s (2.2배)**. Redis는 모든 Run에서 동일하게 cold였으므로, 개선의 원인은 캐시가 DB 쿼리를 흡수한 것이 명확하다.

## Phase 2 — 대기열 batch-size 최적화

**목적**: 캐시 적용으로 DB 병목이 해소된 상태에서, `QueueProcessingScheduler`의 `batch-size`(2초마다 입장 허용할 최대 사용자 수)가 응답 시간에 어떤 영향을 주는지 측정한다.

**고정 조건**: 캐시 ON, pool=30, Virtual Thread, VU=800, `K6_QUEUE_POLL_SLEEP_SEC=0.005`  
**변수**: `ticketing.queue.batch-size` = 30 / 50 / 70

> batch=50 결과는 앞선 캐시 효과 확인 실험(실험 5)에서 획득한 데이터를 그대로 사용한다.

### 실험 4 — batch=30

**가설**: batch를 50에서 30으로 줄이면 큐 처리 속도가 느려져 사용자가 더 오래 폴링하고, p95가 높아질 것이다.

**조건**: `ticketing.queue.batch-size=30`  
2초마다 최대 30명 입장 허용. VU=800 기준 즉시 입장(threshold=30) 제외 ~770명 대기 시 처리 소요 시간 ≈ 770÷30×2s = **51초**

#### 3회 결과

| 회차 | p(95) | p(90) | avg | 에러율 | RPS |
|------|-------|-------|-----|--------|-----|
| 1회 | 5.90 s | 2.08 s | 1.55 s | 0.00% | 326.4/s |
| 2회 | 578 ms | 377 ms | 657 ms | 0.00% | 781.0/s |
| 3회 | 417 ms | 312 ms | 604 ms | 0.00% | 841.3/s |
| **중앙값** | **578 ms** | **377 ms** | **657 ms** | **0.00%** | **~781/s** |

> 대표 결과: 2회차

![batch=30 Grafana 2회차](../portfolio/4.%20캐시후_poolsize30_batchsize30_VT_vu800_0.005/2회차.png)
*대기열 인원(파란 영역)이 batch=50보다 크고 오래 유지됨 — 처리 속도가 느려 사용자가 더 오래 폴링*

#### 해석

1회차 p95=5.9s는 JVM cold start에 batch=30의 느린 큐 처리가 겹친 결과다. 초반 800명이 queue에 쌓이는 속도보다 빠져나가는 속도(30명/2초)가 훨씬 느려 일부 요청의 지연이 누적됐다. batch=50 Run 1(1.51s)보다 훨씬 높게 나온 이유가 여기 있다.

2·3회차 중앙값 p95=578ms는 batch=50(444ms)보다 **30% 높다**. RPS도 781/s로 batch=50(834/s)보다 낮다. 원인은 명확하다. batch=30이면 사용자당 queue에서 보내는 시간이 길어지고, 그 시간 동안 더 많은 폴링 요청이 발생해 전체 처리 비용이 높아진다.

에러는 0%로 시스템은 안정적이나 처리 효율이 낮다.

> **결론**: batch=30은 안정적이지만 과도한 보수 설정이다. 큐 처리 속도 부족으로 p95가 batch=50보다 30% 높고 RPS는 낮다.

**가설 기각 — batch를 늘린다고 p95가 낮아지지 않는다**

2·3회차 중앙값 p95=528ms로, batch=50(444ms)보다 **19% 높다**. 에러는 0%로 안정적이지만 처리 효율은 오히려 떨어졌다.

원인: `QueueProcessingScheduler`는 매 틱마다 가용 좌석 수를 계산하기 위해 `seatRepository.countByConcertId`, `countByConcertIdAndStatus`를 **직접 DB에 조회**한다(이 경로는 `@Cacheable` 미적용). batch가 클수록 스케줄러가 한 틱에 처리할 토큰이 많아져 Redis 호출 횟수도 비례해 증가하고, DB 카운트 쿼리도 더 자주 실행된다. Grafana에서 DB active/pending 스파이크가 batch=50보다 높게 찍힌 것이 이를 증명한다.

> **결론**: batch=70은 큐 처리 속도는 빠르지만 스케줄러의 Redis·DB 오버헤드가 함께 커져 오히려 p95가 높아진다.

---

### Phase 2 종합 — batch-size 최적값

| batch-size | p95 중앙값 | RPS 중앙값 | 에러율 | 특이사항 |
|------------|----------|----------|--------|---------|
| 30 | 578 ms | ~781/s | 0% | 큐 처리 느림 → 폴링 누적 |
| **50** | **444 ms** | **~834/s** | **0%** | **최적** |
| 70 | 528 ms | ~793/s | 0% | 스케줄러 오버헤드 증가 |

**batch=50이 이 하드웨어·VU 조건에서 최적값이다.**

- **30 미만**: 큐 처리 속도 부족 → 사용자 폴링 시간 길어짐 → p95 상승
- **50**: 처리 속도와 스케줄러 오버헤드의 균형점
- **70 이상**: 스케줄러 자체의 Redis·DB 부하 증가 → 오히려 p95 상승

결과가 단순히 "클수록 좋다"가 아닌 **역U자 곡선**을 그리는 이유는, batch-size가 두 가지 상반된 힘에 동시에 작용하기 때문이다.
- 크면 → 사용자 대기 시간 감소 (좋음)
- 크면 → 스케줄러 틱당 처리 비용 증가 (나쁨)

이 균형점이 현재 설정에서는 **50**으로 측정됐다.

## Phase 3 — 스케일아웃 효과 검증 (앱 서버 1대 → 2대)

**목적**: nginx 로드밸런싱으로 앱 서버를 2대로 늘렸을 때 실측 처리량 개선을 수치로 증명한다.  
서버를 2배로 늘리면 TPS가 이론적으로 ~1.8배 향상되어야 한다 — 이 가설을 검증한다.

**비교 방법**
- **1대 기준선**: Phase 2 실험 5 결과 재사용 (캐시 ON, pool=30, VT, batch=50, VU=800 동일 조건)

> **결론**: 앱 서버 2대 + nginx 구성에서 p95 **▼ 63%**, RPS **▲ 73%** 달성. 이론(1.8배)에 근접한 스케일아웃 효과 확인. 공유 자원(Redis·DB·nginx)이 완전한 선형 확장의 상한을 결정한다.

## Phase 4 — VU 1500 한계 부하 검증

**목적**: 스케일아웃(2대) 구성에서 VU를 800에서 1500으로 올렸을 때 시스템이 어떻게 반응하는지 측정한다. "에러 없음"과 "지연이 짧음"은 별개 기준임을 증명하고, 이 구성의 안정 운영 한계 VU를 확인한다.

### 해석

#### VU를 늘렸는데 RPS가 오히려 줄었다

이 실험에서 가장 중요한 관측은 **VU를 800 → 1500으로 1.875배 늘렸음에도 RPS가 1447/s → 1177/s로 오히려 감소**했다는 점이다.

| 구성 | VU | p(95) | RPS | 에러율 |
|------|----|-------|-----|--------|
| 2대, VU=800 (Phase 3) | 800 | 164ms | 1447/s | 0% |
| **2대, VU=1500 (Phase 4)** | 1500 | **1.74s** | **1177/s** | **3.41%** |

VU가 늘어났는데 처리량이 줄고 에러가 발생하는 것은 **시스템이 포화 상태에 진입했다는 전형적인 신호**다. VU=800이 이 구성에서 안정적 처리량을 낼 수 있는 상한에 가까웠음을 의미한다.

#### 1회차 이상치 — JVM cold start + 초기 트래픽 폭발

1회차(에러율 6.83%, p95=4.49s)는 다른 실험과 동일하게 JVM cold start로 설명된다. 단, VU=1500이 동시에 램프업하면서 초기 요청 폭발이 VU=800 실험의 1회차보다 훨씬 강하게 서버를 압박했다. JVM이 JIT 최적화 전 상태에서 1500명의 초기 rush를 받아낸 결과다.

2·3회차 수치가 수렴(에러율 3.41%/2.87%, p95 1.74s/1.56s)하므로 중앙값 기준으로 분석한다.

#### 대기열 진입 25% 실패 원인

VU=800에서는 대기열 진입 에러가 없었으나 VU=1500에서 25%가 실패한다. 원인은 두 가지 조합으로 분석된다.

1. **Rate Limit 초과**: 1500명이 동시에 `/api/queue/enter`를 호출하는 피크 순간, Redis Sliding Window Rate Limiter가 임계(10 req/s/user)를 초과한 요청에 429를 반환한다.
2. **서버 순간 포화**: max=42~59s에 달하는 극단적 지연과 `min=0s` (즉시 실패) 분포가 공존하는 것은 일부 요청이 연결 자체를 얻지 못하고 즉시 실패하는 패턴이다.

`{ expected_response:true }` 기준 p95=529ms로, 실제로 응답을 받은 요청은 빠르게 처리됐다. 에러의 대부분은 연결 혼잡 구간에서 발생한 것이다.

#### "에러 없음"과 "지연이 짧음"은 별개다

이전 실험(VU=800)에서 에러 0%를 달성한 동일 구성이 VU=1500에서 에러를 낸다. p95=1.74s 자체는 준수하지만 에러율 3.41%는 운영에서 허용할 수 없다. **SLO를 설계할 때 p95뿐 아니라 에러율을 별도 기준으로 잡아야 하는 이유**가 여기에 있다.

> **결론**: VU=1500은 이 구성(2대 t3a.small)의 안정적 운영 한계를 초과한다. VU=800에서 에러 0%, VU=1500에서 에러 3.41%로, **안정 운영 상한은 VU=800~1500 사이**에 존재한다. 정확한 knee point는 Phase 5 ramp 시나리오에서 확인한다.

## Phase 6 — 좌석 동시 선점 정확성 검증 (Concurrent Hold Correctness)

**목적**: 100명이 동일 좌석에 동시에 선점을 시도할 때 Redis 분산 락(SETNX + Lua 원자 연산)이 "정확히 1명만 성공" 불변식을 지키는지 증명한다. 성능 측정이 아닌 **정확성(Correctness) 검증**이므로 별도 시나리오로 분리한다.

**시나리오**: `shared-iterations` executor — 100 VU × 100 iterations를 최대한 동시에 실행하여 단일 좌석(seatId=6000)에 경합을 집중시킨다.

**기대 결과**:

| 응답 코드 | 의미 | 기대 건수 |
|-----------|------|----------|
| 201 Created | 선점 성공 | 정확히 1건 |
| 409 Conflict | 이미 선점됨 (Lua EXISTS 확인) | N-1건 수준 |
| 429 Too Many Requests | 락 경합 실패 (lock timeout) | 0~소수건 |
| 5xx | 서버 오류 | 0건 |

### 해석

#### 분산 락 동작 확인

**201 선점 성공 1건** — Redis 분산 락이 100명의 동시 경합에서 정확히 1명만 통과시켰다. 이것이 이 테스트의 핵심 증명이다.

429 응답 93건은 lock wait timeout으로 인한 즉시 거부다. 409 응답 6건은 락 획득에는 성공했으나 이미 선점된 좌석을 확인하고 반환한 것이다. 5xx가 0건이므로 극한 경합 상황에서도 서버가 안정적으로 동작한다.

#### 0×201 — API 응답 코드 버그 (수정 완료)

가장 중요한 관측은 **201 성공이 단 한 건도 없다**는 점이다. 그러나 `http_req_failed` 통계를 역산하면 실제로는 1건의 hold가 성공했음을 알 수 있다.

- 총 101건 HTTP 요청 (login 1건 + hold 100건)
- 비실패 2건 = login(200) + **hold 응답 1건**
- 실패 99건 = 8×409 + 91×429

hold 응답 1건이 비실패임에도 `201 선점 성공` check에서 0/100이 나온 것은 **서버가 201 대신 200을 반환하는 버그** 때문이었다. `HoldController.createHold()`가 `ResponseEntity` 없이 `HoldResponse`를 직접 반환해, Spring이 기본 200 OK를 적용한 것이다.

실제 흐름은 정상이었다: 1명이 락 획득 → 홀드 성공(200 반환) → 이후 8명이 락 획득했으나 이미 홀드된 좌석 발견 → 409 → 91명은 락 타임아웃 → 429.

**수정 내용**: `@ResponseStatus(HttpStatus.CREATED)` 어노테이션 추가로 201 반환하도록 수정 → 재실행에서 **201: 1건** 확인 완료.

#### http_req_failed 임계값 오탐 (false alarm)

`http_req_failed: rate<0.01` 임계값이 98.01%로 위반됐으나 이는 **이 테스트 시나리오에서 예상된 결과다**. k6는 기본적으로 4xx(409, 429)를 실패로 집계하지만, 동시 선점 정확성 테스트에서 409·429는 올바른 동작이다. `concurrent-hold.js` 스크립트 주석에도 이 임계값을 의도적으로 사용하지 않는다고 명시되어 있으나, 외부 설정(k6 config 파일 또는 환경)에서 기본 임계값이 주입된 것으로 보인다.

---

### 보완 사항

#### 1. concurrent-hold.js에 http_req_failed 임계값 명시적 억제

```javascript
thresholds: {
  'checks{check:5xx 없음}': ['rate>0.99'],
  'checks{check:201 선점 성공}': ['rate<=0.02'],
  http_req_failed: ['rate<1'],   // 이 시나리오에서 4xx는 정상 응답 — false alarm 억제
},
```

#### 2. 429 비율 91~94% 해석

기대치 "0~소수건"보다 훨씬 높으나 버그가 아니다. Redis 락 wait timeout이 짧아 대부분의 요청이 락 대기 중 fail-fast 처리된다. 운영 관점에서는 올바른 동작이다(큐잉 방지). 409 분포를 더 넓게 보고 싶다면 lock wait time을 늘릴 수 있다.
