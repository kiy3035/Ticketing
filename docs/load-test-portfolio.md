# 부하 테스트 — 병목 진단 & 한계 탐지

> 이 문서는 **트러블슈팅 여정**의 데이터 부록입니다.
> 핵심 트러블슈팅 서사는 [`backend-portfolio.md` 4장](backend-portfolio.md#4-트러블슈팅-사례)에 있고,
> 이 문서에서는 각 Phase의 가설·실험 조건·실측 수치·Grafana 증거를 정리합니다.

## 개요

| 항목 | 내용 |
|------|------|
| **도구** | k6 |
| **시나리오** | `queue-flow.js` (대기열 진입 → 순번 폴링 → 입장 확인), `concurrent-hold.js` (동시 선점), `knee-point.js` (ramp) |
| **관측** | Prometheus + Grafana 6패널 (RPS · HTTP p95 · DB active/pending · 대기열 · JVM threads) |

| **Run 1 특성** | JVM cold start. 모든 실험에서 일관되게 느림 — 분석 제외 |

## Phase 1 — DB 병목 진단

**목적**: `GET /api/queue/status` 폴링이 DB 쿼리 3회(`countByConcertId`, `countByStatus`, `findSeatIds`)를 매번 실행하는 구조에서, 풀 크기와 Virtual Thread가 성능에 미치는 영향을 측정.

**고정 조건**: 캐시 미적용, VU=800, `K6_QUEUE_POLL_SLEEP_SEC=0.005`

### 실험 결과 (중앙값)

| 실험 | 조건 | p95 | RPS | 에러율 | JVM threads |
|------|------|-----|-----|--------|-------------|
| 1. pool=10 (기준선) | Hikari max=10, VT off | 1.93s | ~408/s | 0% | ~225개 |
| 2. pool=30 | Hikari max=30, VT off | 1.85s | ~386/s | 0% | ~225개 |
| 3. pool=30 + VT | Hikari max=30, VT on | 2.06s | ~376/s | 0% | **~30개** |

세 실험이 p95 1.8~2.1s에서 수렴. 풀과 스레드 모델 모두 진짜 병목이 아님을 가리킴.

![pool=10 Grafana](../portfolio/1.%20캐시전_poolsize10_batchsize50_vu800_0.005/2회차.png)
*pool=10: DB active 풀 한계까지 포화 + pending 다수 적체*

![pool=30+VT Grafana](../portfolio/3.%20캐시전_poolsize30_batchsize50_VT_vu800_0.005/2회차.png)
*pool=30+VT: JVM threads ~225 → ~30 급감, DB 패턴은 동일*

### 진단

VU=800이 5ms 간격으로 폴링 → **초당 수천 건 COUNT 쿼리**. 풀을 10→30으로 늘렸음에도 **DB pending 적체가 해소되지 않음** — 커넥션을 더 줘도 DB가 받는 쿼리 자체가 너무 많아 적체가 풀리지 않는 것.
**병목은 커넥션 수가 아니라 쿼리 빈도.** 해결 방향: 폴링마다 DB를 치는 구조 변경 → 잔여석을 Redis에 캐시.

> **Virtual Thread는 효과가 없었나?** JVM threads 225→30(87% 감소)이라는 명확한 효과는 있다. 단, 이 시나리오에서 처리량의 병목이 DB 쿼리 빈도이므로 RPS 개선으로는 이어지지 않았다. 캐시와 조합 시 진가 발휘(다음 섹션).

## Phase 3 — batch-size 최적화 (최적점 탐색)

**목적**: `QueueProcessingScheduler.batch-size`(2초마다 입장 허용할 최대 사용자 수)가 응답 시간에 미치는 영향.

**고정 조건**: 캐시 ON, pool=30, VT, VU=800

| batch-size | p95 | RPS | 비고 |
|------------|-----|-----|------|
| 30 | 578ms | ~781/s | 큐 처리 느림 → 폴링 누적 |
| **50** | **444ms** | **~834/s** | **최적** |
| 70 | 528ms | ~793/s | 스케줄러 자체 Redis·DB 오버헤드 증가 |

![batch=70 Grafana](../portfolio/6.%20캐시후_poolsize30_batchsize70_VT_vu800_0.005/2회차.png)
*batch=70: DB active/pending 스파이크가 batch=50보다 높음*

**해석**: batch-size는 두 힘의 균형 — 크면 사용자 대기시간 감소(좋음) ↔ 크면 스케줄러 틱당 처리비용 증가(나쁨). 현재 하드웨어에서 균형점은 **50** (p95는 U자, RPS는 역U자 — 두 지표 모두 batch=50에서 최적점 일치).

## Phase 4 — 스케일아웃 (1대 → 2대 nginx)

**목적**: 앱 서버 2대 + nginx `least_conn` 환경에서 처리량이 이론치에 얼마나 근접하는지 측정.

**조건**: 캐시 ON, pool=30, VT, batch=50, VU=800

| 구성 | p95 | RPS | 에러율 |
|------|-----|-----|--------|
| 1대 | 444ms | ~834/s | 0% |
| **2대 (nginx)** | **164ms** | **~1,447/s** | **0%** |
| **개선율** | **▼ 63%** | **▲ 73%** | - |

![2대 nginx Grafana](../portfolio/7.%20캐시후_nginx_poolsize30_batchsize50_VT_vu800_0.005/2회차.png)
*nginx `least_conn` 환경에서 처리 안정 — 실측 분배 비율 app1:app2 = 50.9%:49.1% (VU=800, 총 245,506건 기준)*

> **재현성 검증**: hot JVM 2회 재측정 평균 p95=135ms, RPS=1,621/s, 에러율 0%. 회차 간 변동 9% 내, 문서 기록값(164ms / 1,447/s)과 동등 이상.

이상적 선형 확장은 2배(~1,668/s). 실측은 1.74배(~1,447/s)로 효율 약 87%. 차이는 공유 자원(Redis/MySQL/nginx) 오버헤드·네트워크 RTT·분산 락 경합에서 발생. DB·Redis가 단일 인스턴스인 분산 환경에서 일반적인 효율 구간(80~95%) 내 양호한 수치.

> 균등 분배가 확인됐으니 한 서버 다운 시 나머지 1대로 트래픽이 자동 전이되어 사용자 영향이 최소화되는지는 **Phase 8 페일오버 테스트**에서 별도 검증.

**p95 444ms → 164ms 급감**: 부하 분산으로 각 서버의 Redis 락 경합·DB pending이 감소.

## Phase 5 — VU=1500 한계 부하

**조건**: 2대 nginx 구성, VU=800 → 1500 (1.875배)

| 구성 | VU | p95 | RPS | 에러율 |
|------|----|-----|-----|--------|
| 2대 (Phase 4) | 800 | 164ms | 1,447/s | 0% |
| **2대** | **1,500** | **1.74s** | **1,177/s** | **3.41%** |

![VU=1500 Grafana](../portfolio/8.%20캐시후_nginx_poolsize30_batchsize50_VT_vu1500_0.005/2회차.png)
*VU=1500 한계 부하 — 처리량 plateau 유지되나 DB pending spike 발생, 시스템 포화 신호 시각화*

> **재현성 검증**: hot JVM 2회 재측정 평균 p95=1.38s, RPS=1,455/s, 에러율 2.90%, 진입 성공률 77.5%. 회차 간 변동 7% 내, 문서 기록값(1.74s / 3.41% / 75%)과 ±15% 일치.

**핵심 관측**: VU를 1.875배 늘렸는데 **RPS가 오히려 1,447 → 1,177/s로 감소**. 시스템 포화의 전형적 신호.

**체크 항목별 실패율**

| 체크 | 성공률 | 실패율 |
|------|--------|--------|
| 대기열 진입 201 | 75% | **25%** |
| 순번 조회 200 | 97% | 3% |

**진입 25% 실패 원인 분석**
1. **Rate Limit 초과**: 1,500명 동시 `/api/queue/enter` → Sliding Window가 임계(10 req/s/user) 초과 분에 429
2. **순간 포화**: `http_req_duration` **max=40.02s** (k6 기본 timeout 60s 미만 → 실제 응답 받음), **min=295µs**(즉시 응답)와 공존 — 동일 시점에 일부 요청은 즉시 처리되고 일부는 40초 이상 대기, 포화 구간 응답 시간 분포가 극단으로 갈라짐

`{ expected_response:true }` 기준 p95=529ms — 응답을 받은 요청 자체는 빠르게 처리됨. 에러는 연결 혼잡 구간에 집중.

> **교훈**: "에러 없음"과 "지연이 짧음"은 별개. p95=1.74s 자체는 봐줄 만해도 에러율 3.41%는 운영 불가. SLO는 두 지표를 별도 기준으로.

## Phase 6 — Knee Point 탐지 (ramp 시나리오)

**목적**: VU=800은 안전, VU=1500은 위험 — **정확한 변곡점**을 찾아 SLO 기준 수립.

**스크립트**: `knee-point.js` (VU 500→800→1000→1200→1500, 각 1분, 총 5분 30초)

### 시행착오 3회

| 회차 | 문제 | 수정 |
|------|------|------|
| 1 | `queue-flow.js` stress profile — 단일 피크라 ramp 아님 | `knee-point.js` 신규 작성 |
| 2 | 진입 실패 시 `sleep(1)` 후 즉시 재시도 → Rate Limiter 연쇄 (성공률 21%) | `sleep(5)`로 변경 |
| 3 | `MAX_POLLS=1000` (~4분) → 600+ VU 동시 폴링 → 5xx (순번 조회 30% 실패) | `MAX_POLLS=300` 으로 축소 |

> `MAX_POLLS=300` 근거: VU=1500 큐 드레인 60s ÷ poll 1회 ~235ms = 255회 필요 → 여유 포함 300

### 4회차 — 최종 유효 결과

| 지표 | 값 |
|------|----|
| p95 | 494ms |
| 에러율 (`http_req_failed`) | 4.90% |
| RPS (k6 summary) | 2,324/s *(ramp 시나리오 평균 — Phase 5 stress 시나리오와 부하 모델·폴링 길이가 달라 절대값 직접 비교는 부적절)* |
| 대기열 진입 성공률 | 86% |
| 순번 조회 성공률 | 95% |
| 총 소요 시간 | 5m 30s (정상 완주) |

> **재현 검증 (5회차)**: 동일 조건 재실행에서 p95=448ms, 에러율=3.20%, RPS=2,428/s. 4회차와 동일 추세(VU=1000~1200 구간 EOF·평탄화) 재현. 단, `http_req_duration max=1m0s`(k6 기본 timeout) — VU=1500 구간에서 일부 요청이 응답을 받지 못하고 60초에 잘림. 즉 한계 초과 시 일부 사용자는 timeout까지 기다리다 끊기는 운영 위험 존재 → "VU=800 안정 상한" 결론을 강화하는 근거.

![Knee Point Grafana](../portfolio/9.%20knee_point%20찾기/1회차.png)
*RPS 곡선이 VU=1000~1200 구간에서 평탄화 → DB pending 스파이크·EOF 발생. JDBC active·pending 패널의 5개 톱니 spike는 knee-point.js의 VU 단계(500/800/1000/1200/1500)와 정확히 매핑.*

> **재측정 검증**: hot JVM 재측정에서 p95=537ms, RPS=2,322/s, 에러율=2.59%, 진입 성공률 87%. 문서 5회차값과 ±20% 이내 일치, `max=1m0s` timeout도 동일 재현 → "VU=800 안정 상한" 결론 재차 확인.

### Knee Point 식별 — 두 지표가 같은 구간을 가리킴

1. **k6 WARN[0178] EOF**: 178초 = VU=1000→1200 전환 시점. 서버가 처음으로 연결을 끊기 시작
2. **Grafana RPS 곡선**: 같은 구간에서 상승 정지 후 평탄화

| VU 구간 | 에러율 | 판정 |
|---------|--------|------|
| ≤ 800 | 0% | ✅ 안정 운영 |
| **1,000~1,200** | **EOF 시작** | ⚠️ **Knee Point** |
| ≥ 1,500 | 3.41% | ❌ 한계 초과 |

> **결론**: t3a.small 2대 + nginx 구성의 **안정 처리 상한 VU=800 (~1,447 RPS)**, Knee Point는 **VU=1,000~1,200**.

## Phase 7 — 좌석 동시 선점 정확성 (Correctness)

**목적**: 100명이 동일 좌석에 동시 선점 시 Redis 분산 락이 "정확히 1명만 성공" 불변식을 지키는지 증명. 성능이 아닌 **정확성** 검증.

**시나리오**: `concurrent-hold.js` (`shared-iterations` executor, VU=100, 총 100 iter 분담, 단일 좌석)

**조건**: 매 실행 전 `redis-cli FLUSHDB` + 좌석 DB 초기화(`status=AVAILABLE`, `seat_hold` 삭제), JVM HOT 상태. 각 구성 10회 독립 시행.

### 핵심 결론

**20회 독립 시행(1대×10 + 2대×10) 전부 201=정확히 1건.** Redis가 단일 잠금 저장소이므로 요청이 nginx를 거쳐 2대에 분산되어도 락의 원자성이 유지됨을 통계적으로 증명.

409(이미 선점)와 429(락 경합) 비율은 회차·구성마다 달라지지만 이는 정상 — 타이밍에 따라 락 단계에서 걸리면 429, 락 통과 후 이미 선점 상태를 확인하면 409로 분기될 뿐, 두 경로 모두 중복 선점을 막는 올바른 동작이다.

### 부수 발견 — API 응답 코드 버그

초기 검증에서 `201 선점 성공` 체크가 0건. 그러나 `http_req_failed` 역산하면 1건은 비실패였다.
원인: `HoldController.createHold()`가 `ResponseEntity` 없이 `HoldResponse`를 직접 반환 → Spring 기본 200 OK.
조치: `@ResponseStatus(HttpStatus.CREATED)` 추가 → 재실행에서 201 정상 반환 확인.

> **교훈**: 부하 테스트가 "통과/실패"가 아닌 **응답 코드 분포**까지 셈할 때 비로소 컨트롤러 결함을 잡는다.

### 부수 보완 — http_req_failed false alarm

k6 기본은 4xx를 실패로 집계. 이 시나리오에서 409/429는 정상 응답. `http_req_failed: rate<1` 임계값 명시로 false alarm 억제.

## Phase 8 — 페일오버 (앱서버 1대 다운 시 사용자 영향)

**목적**: 부하 중 앱서버 1대를 강제 다운시켜도 nginx가 자동 격리하고 살아있는 1대로 트래픽이 전이되는지, 그리고 사용자에게 어느 정도 에러가 노출되는지 정량화.

**환경**: VU=800 (안정 운영 상한), 2대 nginx, 캐시 ON, PEAK_HOLD=180s, k6 `queue-flow.js`. 매 회차 전 `redis-cli FLUSHDB`.

**타이밍**: T+150s(PEAK 90초 후) 앱서버1 `docker kill` → T+180s `docker start`. 30초 다운 윈도우.

**nginx 설정**: `least_conn`, `max_fails=2 fail_timeout=10s`, `proxy_next_upstream error timeout http_502 http_503 http_504`, `proxy_next_upstream_tries 2` (passive health check).

### 결과 (1회차·2회차 평균)

| 지표 | 1회차 | 2회차 | 평균 |
|------|------|------|------|
| http_req_failed | 20.74% | 20.80% | **20.77%** |
| http_req_duration p95 | 287ms | 206ms | 246ms |
| http_req_duration max | 1m0s | 1m0s | 1m0s (k6 timeout) |
| 진입 성공 건수 | 3,460 | 3,582 | - |
| 순번 조회 성공률 | 99% | 99% | 99% |

> **에러율 20.74% ↔ 20.80%로 거의 완벽 재현.** 측정 노이즈가 아니라 nginx passive health check의 구조적 결과 — kill 후 nginx가 server1을 격리하기까지 ~10초 동안 일부 요청이 죽은 서버에 라우팅되어 timeout/connection refused로 실패함.

![Phase 8 Failover Grafana](../portfolio/10.%20fail%20over%20테스트/2회차.png)
*JVM threads 패널(우하): 한 라인이 T+150s에 끊기고 T+180s에 복귀 — server1 kill·restart의 가시적 증거. 처리율 패널(좌상): 합산 RPS 곡선이 끊기지 않음 — server2가 트래픽 흡수.*

### 핵심 관측 — failover는 동작하지만 무료가 아니다

1. **시스템 다운 없음** ✅: 처리율 곡선 연속, 순번 조회 99% 유지. server2가 살아남은 트래픽을 흡수하는 게 패널에서 시각적으로 확인됨.
2. **사용자 에러 ~20%** ⚠️: kill 후 ~10초간 nginx가 server1을 격리하기 전, `proxy_connect_timeout 5s` × 2회 재시도(`proxy_next_upstream_tries`)로 끌려서 `http_req_duration max=60s`에 도달한 요청 발생. 일부 요청은 502/timeout.
3. **재현성**: 두 회차 에러율 0.06%p 차이 — 우연이 아닌 구조적 결과로 확정.

### Trade-off 분석 — 왜 0% 에러는 어려운가

passive health check는 "실제 요청이 실패해야 격리 시작"하는 사후 대응 메커니즘. nginx가 `max_fails=2` 카운트를 채우는 동안 사용자 요청 일부는 반드시 죽은 서버에 라우팅됨. 개선 방향:

| 방향 | 효과 | 비용·리스크 |
|------|------|-----------|
| `proxy_connect_timeout 5s → 1s` | 죽은 서버 응답 대기 시간 단축 → 사용자 에러 감소 | 정상 부하 스파이크에서 false-positive 격리 위험 |
| `max_fails 2 → 1` | 1번 실패에 격리, 격리 속도 ↑ | 일시적 네트워크 흔들림에도 멀쩡한 서버 격리 |
| **active health check** (nginx plus 유료 / `nginx_upstream_check_module` 외부 모듈 / 별도 헬스 프로브 + dynamic upstream / K8s·클라우드 LB) | 죽은 서버를 사용자 요청 전에 미리 발견·격리 → 0에 가까운 에러 가능 | 추가 인프라 또는 라이선스, 운영 복잡도 증가 |
| **클라이언트 retry-with-backoff** | 사용자 단에서 자동 재시도로 에러 숨김 | 클라이언트 구현 필요, 멱등성 보장 필수 |

### 개선 시도 — Ablation 분석으로 효과 정량화

위 trade-off 분석을 실측해 두 개선 레이어의 효과를 분리·결합 측정.

**개선 적용**
- **nginx 튜닝**: `max_fails 2→1`, `fail_timeout 10s→5s`, `proxy_connect_timeout 5s→1s`
- **클라이언트 retry**: 5xx/timeout 발생 시 100ms·200ms·400ms 지수 백오프 (최대 2회). 새 스크립트 `queue-flow-with-retry.js`

**Ablation 매트릭스** (동일 시나리오 30초 kill·restart)

| 조건 | nginx 튜닝 | retry | http_req_failed | 진입 성공률 |
|------|-----------|-------|-----------------|-------------|
| **A. baseline** (1·2회차) | OFF | OFF | 20.77% | (미측정) |
| **B. 튜닝 단독** (5회차) | ON | OFF | **24.51%** ⚠️ | **5%** |
| **C. 결합** (3·4회차 평균) | ON | ON | **11.05%** ✅ | **38%** |

![Phase 8 개선 측정 Grafana](../portfolio/10.%20fail%20over%20테스트/4회차.png)
*튜닝 + retry 결합 측정(4회차). JVM threads(우하): server1 라인이 T+150s에 끊기고 T+180s에 복귀. JDBC pending 거의 0 — 빠른 격리 효과 시각화.*

### 결정적 발견 — 가설이 뒤집힘

처음 가설은 "nginx 튜닝 + retry 결합 → 에러 감소". 실측 결과:

1. **nginx 튜닝 단독(B)은 baseline(A)보다 +3.74%p 악화, 진입 성공률 5%로 폭락** — `max_fails=1`·`connect_timeout=1s`가 VU=800 정상 부하에서 **false-positive 격리** 트리거. 정상 서버가 1초 안에 응답 못 하면 즉시 격리 → 트래픽이 다른 서버로 몰림 → 그 서버도 timeout → cascading isolation. 이는 nginx.conf 주석에 미리 적은 트레이드오프 위험이 측정으로 확정된 사례.
2. **retry 레이어가 개선의 주역** — 결합 효과 -47% 중 retry 단독 기여(B→C, -13.46%p)가 거의 전부. nginx 튜닝의 부작용을 retry가 흡수해 진입 5% → 38%로 끌어올림.
3. **운영 권고**: 공격적인 nginx 튜닝값(`max_fails=1`·`connect_timeout=1s`)은 트래픽이 적은 환경에서만 안전. 스트레스 부하에서는 **active HC**가 사실상 유일한 근본 해결책.

**결론**: 오픈소스 nginx + passive HC 단독으로는 **다운타임 30초 시 사용자 에러 ~20%가 구조적 하한**. 클라이언트 retry로 11%까지 흡수 가능하나, **운영 SLO 5% 미만은 active HC 도입 필수**. 이 결론은 ablation으로 정량 검증됨.

> **측정 메트릭 보강**: 1회차 시점에 Prometheus 스크래이프 타겟에 app1만 등록되어 있어 server1 kill 시 모든 패널이 공백으로 보이는 문제 발견. `prometheus.yml`에 app2(172.31.37.7:8080) 추가 후 재측정. 이후 패널 3·4 (DB Pool active/pending)는 인스턴스별 분리(`sum` 미사용)로 server1·server2 라인을 따로 보여주어 failover 동역학을 시각화.

**핵심 발견 5가지**
1. 풀·스레드 모델보다 **쿼리 빈도**가 진짜 병목 (Phase 1·2)
2. batch-size는 **역U자 곡선** — 무조건 클수록 좋지 않음 (Phase 3)
3. 스케일아웃 효과는 이론치의 ~87% 수준, 공유 자원이 상한 결정 (Phase 4)
4. **에러율과 p95는 별도 SLO 지표** — VU=1500에서 p95는 봐줄 만해도 에러율은 운영 불가 (Phase 5·6)
5. **passive health check는 0 에러 failover 불가능** — kill 후 ~10초 격리 지연 동안 사용자 에러 ~20% 발생. nginx 튜닝 + 클라이언트 retry 결합으로 11%까지 흡수 가능하나(-47%), ablation으로 nginx 튜닝 단독은 false-positive 격리로 24.51%로 악화 확인 → **retry가 개선의 주역**, 운영 SLO 5% 미만은 active HC 도입이 필수 조건 (Phase 8)

> **측정 환경 노이즈**: 동일 조건 반복 측정 시 p95·에러율·RPS는 ±10% 내외 변동 관찰됨 (예: Phase 5 에러율 3.41%↔2.90%, Phase 6 4.90%↔3.20%). 추세 결론은 변동 폭보다 큰 차이를 만든 변경(예: 캐시 도입 후 p95 78% 감소)을 기준으로 도출했음.
