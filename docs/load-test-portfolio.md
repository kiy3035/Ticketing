# 부하 테스트 · 포폴 기록 가이드

이 문서는 **knee point·병목** 정리(시나리오 3종)와 **Virtual Thread ON/OFF 비교**를 포폴용으로 남길 때의 **실행 순서**와 **채울 골격**이다. 스크린샷·수치는 실행 후 직접 붙인다.

---

## 권장 실행 순서 (요약)

| 순번 | 스크립트 | 이유 |
|------|----------|------|
| **1** | `db-read.js` | 읽기 위주라 좌석/홀드 상태를 거의 바꾸지 않음. 이후 시나리오에 끼어드는 변수가 적음. |
| **2** | `queue-flow.js` | 대기열·폴링 부하. DB 읽기 병목과 **층을 나눠** 관측하기 좋음. |
| **3** | `seats-hold.js` | 홀드·락·취가 포함된 **가장 공격적인 도메인 쓰기**에 가깝다. 정상이라면 `DELETE`로 홀드가 풀리지만, 앱/DB 부하가 가장 크므로 **마지막**에 두는 편이 해석이 단순하다. |

**Virtual Thread 비교**는 위 3종을 한 바퀴 돌린 뒤 **별도 구간(같은 날 짧게 또는 다른 날)**에 수행한다. 앱 설정만 바꿀 때마다 **동일 k6 파라미터**로만 비교한다.

---

## 크레딧·디스크(20 GiB) 절약 팁

- **한 번에 스크립트 하나만** 돌려서 원인 붙이기 쉽게 한다.
- **계단마다 피크 유지**는 Prometheus 스크랩(보통 15s) 기준 **최소 1~2분**은 확보하되, 불필요하게 10분 이상 피크를 유지하지 않는다.
- **t3/t3a 버스트 크레딧**: 계단 사이 **5~10분 휴지**를 두면 앱·k6 인스턴스 크레딧 회복에 유리하다.
- 앱 **액세스 로그**가 과하면 디스크·IOPS가 빨리 쓰인다. 부하 구간만 레벨을 낮추는 것을 검토한다.
- k6는 기본적으로 디스크를 크게 쓰지 않는다. 결과는 터미널 요약 + (선택) `--summary-export` JSON 정도로 충분한 경우가 많다.

- [ ] `BASE_URL`, `CONCERT_ID` 고정
- [ ] `db-read` / `seats-hold`: `TEST_USER` / `TEST_PASS` 유효
- [ ] knee 탐색 시: `K6_PROFILE=stress` (threshold 완화)
- [ ] Grafana/Prometheus 시간 범위가 테스트 구간과 겹치도록 맞춤

**공통 env 예시** (필요 시만 조정):

```bash
# 곡선은 모든 실행에서 동일하게 두고, K6_PEAK_VU만 계단마다 바꾸는 것을 권장
-e K6_WARM_DURATION=15s -e K6_MID_DURATION=30s -e K6_CLIMB_DURATION=30s \
-e K6_PEAK_HOLD=90s -e K6_RAMP_DOWN=15s
```

## Phase 2 — Virtual Thread 사용 여부 비교

**전제**: 앱 코드·인스턴스 스펙·JVM 옵션은 동일하고, **Virtual Thread 활성화 여부만** 바꾼다.

**권장 대표 시나리오** (하나만 골라도 되고, 둘 다 하면 더 좋음)

| 우선순위 | 스크립트 | 이유 |
|----------|----------|------|
| 1 | `queue-flow.js` | 동시에 대기하는 요청이 많아 **스레드 모델 차이**가 그래프에 잘 드러나는 편 |
| 2 | `seats-hold.js` | 도메인 스토리와 함께 **홀드 경로**에서의 차이를 보여 주기 좋음 |

**실행 순서 (크레딧 절약)**

1. 앱을 **Platform 스레드(VT OFF)** 로 기동 → k6 **한 번** (아래 표의 고정 파라미터).
2. 앱을 **Virtual Thread(VT ON)** 로 기동 → **동일 k6 커맨드**로 **한 번**.
3. (선택) VU를 **한 단계만** 더 올려 위 1~2를 반복 — 최대 4회(VT×VU 2단계)면 비교 문장이 충분히 나온다.

**고정할 k6 파라미터** (반드시 양쪽 동일)

- 스크립트 이름, `BASE_URL`, `CONCERT_ID`, `K6_PEAK_VU`, `K6_PROFILE`, stage 관련 env 전부

**비교 표**

| 항목 | VT OFF | VT ON |
|------|--------|-------|
| 스크립트 | | |
| K6_PEAK_VU | | |
| k6 p95 (http_req_duration) | | |
| k6 에러율 | | |
| `jvm_threads_live_threads` (피크 근처) | | |
| 기타 패널 (Tomcat busy, RPS 등) | | |

**스크린샷**

| 설명 | VT OFF | VT ON |
|------|--------|-------|
| JVM 스레드 | ![](./images/vt-off-threads.png) | ![](./images/vt-on-threads.png) |
| HTTP p95 / RPS | ![](./images/vt-off-http.png) | ![](./images/vt-on-http.png) |

**한 줄 결론**

(예: 동일 VU에서 p95가 OO% 변화, 피크 스레드 수는 VT ON에서 더 낮게 유지 등 — 수치로 채운다.)
