# 부하 테스트 — 병목 진단 & 한계 탐지

> 이 문서는 **트러블슈팅 여정**의 데이터 부록입니다.
> 핵심 트러블슈팅 서사는 [`backend-portfolio.md` 4장](backend-portfolio.md#4-트러블슈팅-사례)에 있고,
> 이 문서에서는 각 Phase의 가설·실험 조건·실측 수치·Grafana 증거를 정리합니다.

## 개요

| 항목 | 내용 |
|------|------|
| **도구** | k6 |
| **시나리오** | `queue-flow.js` (대기열 진입 → 순번 폴링 → 입장 확인), `concurrent-hold.js` (동시 선점), `knee-point.js` (ramp) |
| **관측** | Prometheus + Grafana 6패널 (RPS · HTTP p95 · DB active/pending · 대기열 · JVM threads) |
| **실행 방식** | 설정 변경 시 앱 재기동, Run 2·3 전 Redis 전체 키 삭제(cold). 중앙값(2·3회차) 기준 분석 |
| **Run 1 특성** | JVM cold start (JIT 미적용). 모든 실험에서 일관되게 느림 — 분석 제외 |

## Phase 1 — DB 병목 진단

**목적**: `GET /api/queue/status` 폴링이 DB 쿼리 3회(`countByConcertId`, `countByStatus`, `findSeatIds`)를 매번 실행하는 구조에서, 풀 크기와 Virtual Thread가 성능에 미치는 영향을 측정.

**고정 조건**: 캐시 미적용, VU=800, `K6_QUEUE_POLL_SLEEP_SEC=0.005`

### 실험 결과 (중앙값)

| 실험 | 조건 | p95 | RPS | 에러율 | JVM threads |
|------|------|-----|-----|--------|-------------|
| 1. pool=10 (기준선) | Hikari max=10, VT off | 1.93s | ~408/s | 0% | ~225개 |
| 2. pool=30 | Hikari max=30, VT off | 1.85s | ~386/s | 0% | ~225개 |
| 3. pool=30 + VT | Hikari max=30, VT on | 2.06s | ~376/s | 0% | **~30개** |

세 실험이 p95 1.8~2.1s에서 수렴. 풀과 스레드 모델 모두 진짜 병목이 아님을 가리킴.

![pool=10 Grafana](../portfolio/1.%20캐시전_poolsize10_batchsize50_vu800_0.005/2회차.png)
*pool=10: DB active=10 포화 + pending ~170 적체*

![pool=30+VT Grafana](../portfolio/3.%20캐시전_poolsize30_batchsize50_VT_vu800_0.005/2회차.png)
*pool=30+VT: JVM threads ~225 → ~30 급감, DB 패턴은 동일*

### 진단

VU=800이 5ms 간격으로 폴링 → **초당 수천 건 COUNT 쿼리**. 풀을 늘리거나 스레드를 가볍게 만들어도 DB가 처리할 쿼리 수 자체에는 영향이 없다.
**병목은 커넥션 수가 아니라 쿼리 빈도.** 해결 방향: 폴링마다 DB를 치는 구조 변경 → 잔여석을 Redis에 캐시.

> **Virtual Thread는 효과가 없었나?** JVM threads 225→30(87% 감소)이라는 명확한 효과는 있다. 단, 이 시나리오에서 처리량의 병목이 DB 쿼리 빈도이므로 RPS 개선으로는 이어지지 않았다. 캐시와 조합 시 진가 발휘(다음 섹션).

## Phase 3 — batch-size 최적화 (역U자 곡선)

**목적**: `QueueProcessingScheduler.batch-size`(2초마다 입장 허용할 최대 사용자 수)가 응답 시간에 미치는 영향.

**고정 조건**: 캐시 ON, pool=30, VT, VU=800

| batch-size | p95 | RPS | 비고 |
|------------|-----|-----|------|
| 30 | 578ms | ~781/s | 큐 처리 느림 → 폴링 누적 |
| **50** | **444ms** | **~834/s** | **최적** |
| 70 | 528ms | ~793/s | 스케줄러 자체 Redis·DB 오버헤드 증가 |

![batch=70 Grafana](../portfolio/6.%20캐시후_poolsize30_batchsize70_VT_vu800_0.005/2회차.png)
*batch=70: DB active/pending 스파이크가 batch=50보다 높음*

**해석**: batch-size는 두 힘의 균형 — 크면 사용자 대기시간 감소(좋음) ↔ 크면 스케줄러 틱당 처리비용 증가(나쁨). 현재 하드웨어에서 균형점은 **50**.

## Phase 4 — 스케일아웃 (1대 → 2대 nginx)

**목적**: 앱 서버 2대 + nginx round-robin 환경에서 처리량이 이론치(~1.8배)에 얼마나 근접하는지 측정.

**조건**: 캐시 ON, pool=30, VT, batch=50, VU=800

| 구성 | p95 | RPS | 에러율 |
|------|-----|-----|--------|
| 1대 | 444ms | ~834/s | 0% |
| **2대 (nginx)** | **164ms** | **~1,447/s** | **0%** |
| **개선율** | **▼ 63%** | **▲ 73%** | - |

![2대 nginx Grafana](../portfolio/7.%20캐시후_nginx_poolsize30_batchsize50_VT_vu800_0.005/2회차.png)
*두 앱 서버의 CPU·JVM threads 균등 분배 — round-robin 정상 동작*

이론 상한(~1.8배 = ~1,501/s) 대비 실측 ~96% 달성. 공유 자원(Redis/MySQL/nginx)이 완전한 선형 확장의 상한을 결정.

**p95 444ms → 164ms 급감 이유**: 단순 처리 서버 증가뿐 아니라, 부하 분산으로 각 서버의 Redis 락 경합·DB pending이 절반 수준으로 감소.

## Phase 5 — VU=1500 한계 부하

**조건**: 2대 nginx 구성, VU=800 → 1500 (1.875배)

| 구성 | VU | p95 | RPS | 에러율 |
|------|----|-----|-----|--------|
| 2대 (Phase 4) | 800 | 164ms | 1,447/s | 0% |
| **2대** | **1,500** | **1.74s** | **1,177/s** | **3.41%** |

![VU=1500 Grafana](../portfolio/8.%20캐시후_nginx_poolsize30_batchsize50_VT_vu1500_0.005/2회차.png)

**핵심 관측**: VU를 1.875배 늘렸는데 **RPS가 오히려 1,447 → 1,177/s로 감소**. 시스템 포화의 전형적 신호.

**체크 항목별 실패율**

| 체크 | 성공률 | 실패율 |
|------|--------|--------|
| 대기열 진입 201 | 75% | **25%** |
| 순번 조회 200 | 97% | 3% |

**진입 25% 실패 원인 분석**
1. **Rate Limit 초과**: 1,500명 동시 `/api/queue/enter` → Sliding Window가 임계(10 req/s/user) 초과 분에 429
2. **순간 포화**: max 42~59s 극단 지연과 min=0s(즉시 실패)가 공존 — 일부는 연결 자체를 못 얻음

`{ expected_response:true }` 기준 p95=529ms — 응답을 받은 요청 자체는 빠르게 처리됨. 에러는 연결 혼잡 구간에 집중.

> **교훈**: "에러 없음"과 "지연이 짧음"은 별개. p95=1.74s 자체는 봐줄 만해도 에러율 3.41%는 운영 불가. SLO는 두 지표를 별도 기준으로.

## Phase 6 — Knee Point 탐지 (ramp 시나리오)

**목적**: VU=800은 안전, VU=1500은 위험 — **정확한 변곡점**을 찾아 SLO 기준 수립.

**스크립트**: `knee-point.js` (VU 500→800→1000→1200→1500, 각 1분, 총 5분 30초)

### 시행착오 3회

| 회차 | 문제 | 수정 |
|------|------|------|
| 1 | `queue-flow.js` stress profile — 단일 피크라 ramp 아님 | `knee-point.js` 신규 작성 |
| 2 | 진입 실패 시 `sleep(1)` 후 즉시 재시도 → Rate Limiter 연쇄 (성공률 21%) | `sleep(5)`로 변경 |
| 3 | `MAX_POLLS=1000` (~4분) → 600+ VU 동시 폴링 → 5xx (순번 조회 30% 실패) | `MAX_POLLS=300` 으로 축소 |

> `MAX_POLLS=300` 근거: VU=1500 큐 드레인 60s ÷ poll 1회 ~235ms = 255회 필요 → 여유 포함 300

### 4회차 — 최종 유효 결과

| 지표 | 값 |
|------|----|
| p95 | 494ms |
| 에러율 (`http_req_failed`) | 4.90% |
| RPS | 2,324/s |
| 대기열 진입 성공률 | 86% |
| 순번 조회 성공률 | 95% |
| 총 소요 시간 | 5m 30s (정상 완주) |

![Knee Point Grafana](../portfolio/9.%20knee_point%20찾기/1회차.png)
*RPS 곡선이 VU=1000~1200에서 평탄화 → DB pending 스파이크·EOF 발생*

### Knee Point 식별 — 두 지표가 같은 구간을 가리킴

1. **k6 WARN[0178] EOF**: 178초 = VU=1000→1200 전환 시점. 서버가 처음으로 연결을 끊기 시작
2. **Grafana RPS 곡선**: 같은 구간에서 상승 정지 후 평탄화

| VU 구간 | 에러율 | 판정 |
|---------|--------|------|
| ≤ 800 | 0% | ✅ 안정 운영 |
| **1,000~1,200** | **EOF 시작** | ⚠️ **Knee Point** |
| ≥ 1,500 | 3.41% | ❌ 한계 초과 |

> **결론**: t3a.small 2대 + nginx 구성의 **안정 처리 상한 VU=800 (~1,447 RPS)**, Knee Point는 **VU=1,000~1,200**.

## Phase 7 — 좌석 동시 선점 정확성 (Correctness)

**목적**: 100명이 동일 좌석에 동시 선점 시 Redis 분산 락이 "정확히 1명만 성공" 불변식을 지키는지 증명. 성능이 아닌 **정확성** 검증.

**시나리오**: `concurrent-hold.js` (`shared-iterations`, 100 VU × 100 iter, 단일 좌석)

### 결과 — 1대 직접 vs 2대 nginx 분산

| 응답 | 1대 직접 | 2대 nginx |
|------|----------|-----------|
| **201 선점 성공** | **1건** ✅ | **1건** ✅ |
| 409 이미 선점 | 6건 | 0건 |
| 429 락 경합 | 93건 | 99건 |
| 5xx | 0건 | 0건 |
| 전체 소요 | 2.1s | 0.8s |
| p95 | 2.06s | 537ms |

### 핵심 결론

**두 구성 모두 201이 정확히 1건.** 100명이 nginx로 2대에 분산되어도 Redis가 단일 잠금 저장소이므로 락의 원자성이 보존된다. **분산 락 불변식이 분산 환경에서도 유지됨을 증명**.

### 부수 발견 — API 응답 코드 버그

초기 검증에서 `201 선점 성공` 체크가 0건. 그러나 `http_req_failed` 역산하면 1건은 비실패였다.
원인: `HoldController.createHold()`가 `ResponseEntity` 없이 `HoldResponse`를 직접 반환 → Spring 기본 200 OK.
조치: `@ResponseStatus(HttpStatus.CREATED)` 추가 → 재실행에서 201 정상 반환 확인.

> **교훈**: 부하 테스트가 "통과/실패"가 아닌 **응답 코드 분포**까지 셈할 때 비로소 컨트롤러 결함을 잡는다.

### 부수 보완 — http_req_failed false alarm

k6 기본은 4xx를 실패로 집계. 이 시나리오에서 409/429는 정상 응답. `http_req_failed: rate<1` 임계값 명시로 false alarm 억제.

## 종합 — 한 페이지 요약

| 구성 | VU | p95 | RPS | 에러율 |
|------|----|-----|-----|--------|
| 1대, pool=10 (기준선) | 800 | 1.93s | ~408/s | 0% |
| 1대, pool=30 + VT | 800 | 2.06s | ~376/s | 0% |
| **1대, + 잔여석 캐시** | 800 | **444ms** | **~834/s** | **0%** |
| **2대, nginx + 동일 구성** | 800 | **164ms** | **~1,447/s** | **0%** |
| 2대, VU=1500 (한계) | 1500 | 1.74s | ~1,177/s | 3.41% |
| 동시 선점 정확성 (100 VU) | - | - | - | 201: **1건** |

**핵심 발견 4가지**
1. 풀·스레드 모델보다 **쿼리 빈도**가 진짜 병목 (Phase 1·2)
2. batch-size는 **역U자 곡선** — 무조건 클수록 좋지 않음 (Phase 3)
3. 스케일아웃 효과는 이론치의 ~96% 수준, 공유 자원이 상한 결정 (Phase 4)
4. **에러율과 p95는 별도 SLO 지표** — VU=1500에서 p95는 봐줄 만해도 에러율은 운영 불가 (Phase 5·6)
