# 콘서트 티켓 예매 시스템 — 백엔드 포트폴리오

> **한 줄 요약**: 동시 1,000명 이상 접속 환경에서 좌석 중복 예약 0건을 보장하는 콘서트 예매 백엔드.
> Redis 분산 락 · Kafka 이벤트 · Transactional Outbox · Saga 보상 패턴을 직접 구현했고, **부하 테스트로 병목을 진단해 p95를 2.06s → 164ms로 92% 단축**한 트러블슈팅 사례를 보유합니다.

> 🛠️ **개발 도구 활용**: 본 프로젝트는 Claude·Cursor를 적극 활용해 개발했습니다. 시스템 설계·코드 구현·부하 테스트 가설 분석은 AI와 협업했고, 측정 실행·재현성 검증·최종 의사결정은 본인이 직접 수행했습니다. 본 문서의 모든 수치는 실측 결과입니다.

## 1. 프로젝트 개요

| 항목 | 내용 |
|------|------|
| **목적** | 대규모 트래픽 처리·좌석 동시 선점 제어·인프라 운영 경험을 포트폴리오로 증명 |
| **핵심 문제** | ① 공연 오픈 순간 트래픽 폭주 ② 동일 좌석 동시 선점 경쟁 ③ 결제·예약 정합성 보장 |
| **인프라** | t3a.medium(Redis/Kafka/Prometheus/Grafana/nginx) + t3a.small 앱 서버 **2대** + t3a.small k6 |
| **부하 검증** | 안정 운영 상한 VU=800 (1,447 RPS, 에러 0%), Knee Point VU=1,000~1,200 |

### 주요 구현
- JWT Access/Refresh 인증 (Redis Access 블랙리스트 + DB Refresh `revoked` 마킹)
- Redis ZSet 대기열 + 즉시 입장 임계값
- Redis 분산 락(SETNX + Lua) + Lua 원자적 좌석 홀드
- 3단계 결제 플로우 (READY → APPROVED → COMPLETED)
- Saga 보상 트랜잭션 (`REQUIRES_NEW` 분리 커밋)
- Transactional Outbox (예약 확정 이벤트 유실 방지)
- Resilience4j 서킷브레이커 + Sliding Window Rate Limit
- SSE 다중 인스턴스 브로드캐스트 (Redis Pub/Sub `sse:notify:*`)
- Prometheus 커스텀 메트릭 + Grafana 대시보드

## 4. 트러블슈팅 사례 — k6 부하 테스트

> 이 프로젝트에서 가장 시간을 많이 쓴 영역이다. 부하 테스트는 기능 구현과 달리 코드가 컴파일되는 것으로 끝나지 않는다. 측정 환경을 짓고, 시나리오를 짜고, 결과를 의심하고, 다시 측정하는 사이클이 반복됐다. 그 과정에서 부딪힌 트러블슈팅 사례와 검증 결과를 정리한다.
>
> 부록: [부하 테스트 상세 데이터](load-test-portfolio.md)

### 측정 환경부터 시행착오였다

도구는 k6로 정했다. 단일 바이너리 실행, 자바스크립트 시나리오, Grafana 사가 만든다는 점에서 모니터링 스택과 자연스럽게 붙을 거라는 기대가 있었다. JMeter처럼 GUI를 띄울 일이 없고 Locust처럼 파이썬 환경을 별도로 만들 일도 없는 게 좋았다.

문제는 그 다음이었다. 부하 테스트를 *돌리는* 일보다 *결과를 보는* 일이 처음이었다. Prometheus의 `scrape_configs`를 직접 써본 적이 없었고, PromQL은 한 줄도 모르는 상태에서 Grafana 패널을 처음부터 짜야 했다. `rate(hikaricp_connections_active[1m])` 같은 한 줄을 쓰는 데도 공식 문서를 왔다갔다 했다. Hikari 풀 사이즈를 그래프로 보고 싶은데 어떤 메트릭 이름을 골라야 하는지부터 모르는 상태였다.

며칠은 부하 테스트는 잘 돌아가는데 Grafana는 비어 있었다. 그러다 매 회차 사이에 `redis-cli FLUSHDB`로 잔여 키를 지워야 한다는 사실도 한 번 데인 뒤에 알았다. 같은 시나리오를 두 번 돌렸더니 두 번째 RPS가 첫 번째의 절반이었다. 이전 실행에서 큐에 진입한 사용자가 그대로 누적된 결과였다. *측정 결과를 의심하는 감각*이 이때 자리잡혔다.

여기서 두 가지 방침이 굳어졌다. (1) 매 회차 전 Redis FLUSHDB + 좌석 DB 초기화로 상태를 깨끗이 만든다. (2) JVM cold start인 1회차는 분석에서 제외하고 hot 상태인 2·3회차 평균을 기준으로 본다. 부하 테스트의 결과보다 결과를 신뢰할 수 있게 만드는 일이 더 오래 걸렸다.

---

### 사례 1. p95가 떨어지지 않는다 — 풀과 스레드를 다 바꿔도 안 풀리던 문제

기능 구현이 끝나고 부하 테스트에 들어갔다. VU 800으로 큐 폴링 API를 돌렸을 때 처음 본 숫자가 `p95 = 1.93s`였다. 한 자릿수 초가 찍힌 것 자체가 당황스러웠다. 1초가 넘으면 사용자는 "고장났다"고 느낀다.

Grafana를 열었다. `hikaricp_connections_active`가 10에 평탄하게 붙어 있고, `hikaricp_connections_pending`이 톱니파처럼 170 부근까지 올라갔다 내려가길 반복했다. 풀이 좁다고 직관적으로 판단했다.

#### 첫 가설 — 풀이 좁다

Hikari `maximum-pool-size`를 10에서 30으로 올리고 다시 돌렸다. 결과는 의외였다.

| 풀 크기 | p95 | RPS |
|---|---|---|
| 10 | 1.93s | ~408/s |
| 30 | 1.85s | ~386/s |

p95는 80ms 줄었다. RPS는 오히려 22 줄었다. 풀을 3배로 늘렸는데 사실상 차이가 없는 셈이다. Grafana에서 `pending`은 줄어 있었다. 그런데 `p95`는 안 움직였다. 이 시점에는 그게 무슨 의미인지 몰랐다.

#### 두 번째 가설 — Virtual Thread

Java 21을 쓰고 있다는 게 떠올랐다. Virtual Thread를 켜면 I/O 대기 중에 OS 스레드를 잡지 않으니, 같은 풀 안에서도 더 많은 요청을 처리할 수 있을 거라는 막연한 기대가 있었다. `spring.threads.virtual.enabled=true` 한 줄을 추가하고 다시 돌렸다.

```
JVM live threads:  225 → 30   ▼ 87%
p95:               1.85s → 2.06s
RPS:               386 → 376/s
```

스레드는 분명히 줄었다. 그래프에서 `jvm_threads_live` 라인이 한 단계 떨어졌다. 그런데 p95는 *오히려* 올라갔다. RPS도 미세하게 떨어졌다. 두 번째 가설도 빗나간 셈이다.

여기서 한 번 멈췄다. 풀을 늘려도, 스레드 모델을 바꿔도 p95가 1.8~2.1초 구간에 박혀 있다는 건 두 변수 모두 진짜 병목이 아니라는 뜻이다.

#### 그래프를 다시 본 순간

가설을 폐기하고 Grafana 6패널을 처음부터 다시 들여다봤다. 풀 크기를 늘렸을 때 `pending`은 분명히 줄었는데 `p95`는 안 줄었다는 사실이 새삼스럽게 보였다. 두 그래프가 같이 안 움직였다.

여기서 한 줄이 떠올랐다. *pending이 줄어도 p95가 안 줄면, 커넥션 자체는 병목이 아니다.* 커넥션을 더 줘도 처리 시간은 변하지 않는다는 뜻이고, 진짜 풀어야 할 곳은 *DB가 받는 쿼리 자체*였다.

폴링 구조를 따져봤다. `K6_QUEUE_POLL_SLEEP_SEC=0.005` 옵션으로 VU 800이 짧은 간격으로 폴링하고, 폴링 1회마다 `GET /api/queue/status`가 DB 쿼리 3회(`countByConcertId`, `countByConcertIdAndStatus`, `findSeatIdsByConcertId`)를 실행한다. 풀을 늘리면 더 많은 폴링 요청이 동시에 풀 슬롯을 점유할 수 있고, 그 각각이 그대로 DB로 향한다. 즉 *풀이 좁아서 큐에 갇혀 있던 폴링이, 풀을 넓히면 그대로 DB로 풀려나가는* 구조였다.

풀을 10에서 30으로 늘려도, OS 스레드를 가벼운 Virtual Thread로 바꿔도 폴링이 DB를 치는 빈도 자체는 줄지 않는다. 두 변수 모두 *커넥션이 어떻게 사용되는가*에 영향을 주지만, *DB가 받는 쿼리 수*는 변함이 없다. 그래서 p95가 같은 자리에 박혀 있었다.

#### 해결 — 쿼리를 안 치게 만든다

병목이 쿼리 빈도라면 풀이나 스레드를 만지는 건 의미가 없다. 폴링마다 DB를 치는 구조 자체를 바꿔야 한다.

여기서 도메인 판단이 들어갔다. 잔여석 수는 사용자에게 *정확히 실시간*일 필요가 없다. 1~2초 늦은 근사값이어도 "남은 좌석이 많은지 적은지" 판단에는 충분하다. 이 근사 허용도 덕분에 캐시가 가능했다.

`SeatService.countAvailableSeatsForQueueStatus()`에 `@Cacheable(TTL=2s)`을 붙였다. 그리고 캐시가 깨져야 할 시점을 따져봤다 — 홀드 생성, 홀드 해제, 예약 확정, 만료 정리. 이 네 지점에 `@CacheEvict`. 이 무효화 시점을 빠뜨리면 사용자가 좌석을 잡았는데 잔여석에 반영되지 않는 정합성 문제가 생긴다.

#### 결과

| 지표 | 캐시 전 | 캐시 후 | 변화 |
|---|---|---|---|
| p95 | 2.06s | **444ms** | ▼ 78% |
| RPS | ~376/s | **~834/s** | ▲ 122% |
| DB pending | 높음 | 거의 0 | — |

`@Cacheable` 한 줄로 p95가 4분의 1이 됐다. Grafana에서 `connections_pending`이 거의 0까지 떨어지고, `connections_active`도 평탄해졌다. 풀 크기 30이 처음으로 의미를 가진 순간이었다 — 더 이상 풀이 좁지 않고, *DB 자체가 더 이상 핫스팟이 아닌* 상태가 됐다.

한 가지 한계는 이 측정에 남아 있다. 캐시 적용 후 환경은 `pool=30 + VT on` 한 조건만 측정했고, 같은 환경에서 VT off로의 비교 측정은 진행하지 않았다. 즉 *2.2배 RPS 증가*는 본문 그대로 캐시 적용의 효과이지만, 그 안에 Virtual Thread가 얼마나 기여했는지는 이 데이터만으로는 분리할 수 없다. ablation을 완성하려면 캐시 후 VT off 한 케이스를 추가로 측정했어야 한다.

#### 회고

- "p95가 안 떨어지는데 풀이 그래도 부족한가?"라는 직관적 가설을 두 번 시도하고 두 번 다 틀린 게 핵심 경험이다. 만약 데이터를 보지 않고 *느낌*만으로 풀을 60, 100까지 올렸으면 영영 풀지 못했을 것이다.
- 결정적 신호는 *pending은 줄었는데 p95는 안 줄었다*는 두 그래프의 불일치였다. 한 그래프만 봤으면 못 잡았을 신호. 부하 테스트 분석에서 두 메트릭의 상관/비상관을 같이 보는 습관이 그래서 중요했다.
- 캐시는 만능이 아니라 도메인 판단의 결과다. "잔여석 1~2초 근사 허용"이라는 비즈니스 조건이 없었으면 캐시를 못 썼다. 무효화 시점 네 곳을 빠뜨리면 정합성이 깨진다. 캐시 적용은 그 자체로 위험을 들이는 행위라, 무엇을 캐시할 수 있는지 *도메인 측면에서* 먼저 따지는 게 안전했다.
- 다음에 비슷한 상황을 만나면 풀이나 스레드 모델을 만지기 전에 *현재 DB가 받고 있는 쿼리 흐름*부터 모니터링에서 확인한다. 인프라 튜닝은 그 다음이다.

### 사례 2. 측정 도구가 측정 대상이 되어버렸을 때 — Knee Point를 찾는 과정

Phase 1·2를 끝내고 스케일아웃까지 진행한 시점에 안정 상한이 어디인지 궁금해졌다. VU=800에서는 에러 0%, VU=1500에서는 3.41% 에러. 그 사이 어딘가에 *변곡점*이 있을 것이다. 운영 SLO를 정하려면 그 지점을 찾아야 했다.

기존 시나리오 `queue-flow.js`는 stress profile이라 단일 피크 모양이었다. ramp로 단계적으로 올려야 변곡점이 보인다. `knee-point.js`를 새로 작성했다. VU 500 → 800 → 1000 → 1200 → 1500, 각 단계 1분씩.

이때부터 측정 도구 자체가 측정 결과를 흔드는 일이 시작됐다.

#### 1회차 — 시나리오 모양이 틀렸다

처음엔 `queue-flow.js`를 그대로 쓰면서 옵션만 바꿨다. 결과 그래프를 보니 ramp가 아니라 한 번에 올라갔다가 내려오는 모양이었다. stress profile은 step 정의를 무시하고 자체 피크를 만들고 있었다.

→ `knee-point.js`를 새로 작성. step별 VU와 duration을 명시.

#### 2회차 — 클라이언트가 서버를 때렸다

`knee-point.js`로 다시 돌렸더니 진입 성공률이 21%까지 떨어졌다. 한 자릿수 % 가까이로 폭락한 적은 처음이었다.

원인을 찾는 데 시간이 들었다. 시나리오 안에서 진입 실패 시 `sleep(1)` 후 즉시 재시도하도록 짜놨었다. VU 1000명이 동시에 진입 실패하면 1초 뒤에 1000명이 동시에 재시도한다. 서버의 Sliding Window Rate Limiter는 이 패턴을 *공격*으로 인식한다. 한 사용자당 10 req/s 임계를 넘으면 429를 던지는데, 재시도가 동시에 몰리니 모든 재시도가 429를 받았다. 429를 받으니 또 1초 뒤에 재시도. *retry storm*이 만들어진 상태였다.

→ 재시도 간격을 `sleep(5)`로 늘리고 백오프 구조로 변경.

이 시행착오에서 배운 게 컸다. 측정 도구(k6 시나리오)가 측정 대상(서버 처리율)에 영향을 미치고 있었다. 진짜 사용자 행동을 모사한다고 짠 시나리오가 사실은 의도치 않은 부하 패턴을 만들고 있었던 것이다.

#### 3회차 — 폴링이 너무 길었다

이번엔 다른 곳에서 터졌다. `MAX_POLLS=1000`으로 설정했더니, 단계 사이에 VU가 누적되면서 600명 이상이 동시에 순번을 폴링하는 시간대가 생겼다. 5xx가 30% 가까이 발생했다.

`MAX_POLLS`는 각 VU가 큐 안에서 얼마나 오래 순번을 기다리느냐를 결정한다. 1000회면 약 4분. 그동안 다음 단계의 VU가 들어오니 폴링 인구가 누적된다. 폴링은 캐시 덕분에 가볍지만, 인구가 충분히 누적되면 다른 자원이 먼저 터진다.

→ `MAX_POLLS=300`으로 축소. 근거는 단순한 산수다. VU=1500 큐 드레인이 약 60초, 폴 1회 약 235ms → 약 255회면 충분. 여유 포함 300.

#### 4회차 — 드디어 측정이 됐다

세 번 갈아엎고 나서야 측정 가능한 결과가 나왔다.

| 지표 | 값 |
|---|---|
| p95 | 494ms |
| 에러율 | 4.90% |
| RPS | 2,324/s (ramp 평균) |
| 대기열 진입 성공률 | 86% |
| 총 소요 시간 | 5m 30s (정상 완주) |

#### Knee Point 식별 — 두 지표가 같은 구간을 가리켰다

흥미로운 건 결과 자체가 아니라 *두 개의 독립된 신호*가 같은 시점을 가리켰다는 것이었다.

1. **k6 클라이언트 측 신호**: `WARN[0178] EOF` — 178초 시점부터 서버가 처음으로 연결을 끊기 시작. 178초는 정확히 VU=1000에서 1200으로 전환되는 시점.
2. **Grafana 서버 측 신호**: 같은 178초 구간부터 RPS 곡선이 상승을 멈추고 평탄해짐.

| VU 구간 | 에러율 | 판정 |
|---|---|---|
| ≤ 800 | 0% | ✅ 안정 운영 |
| **1,000~1,200** | EOF 시작 | ⚠️ **Knee Point** |
| ≥ 1,500 | 3.41% | ❌ 한계 초과 |

이걸로 운영 SLO 기준이 잡혔다. *t3a.small 2대 + nginx 구성의 안정 처리 상한 VU=800 (약 1,447 RPS), Knee Point는 VU=1,000~1,200.*

#### 회고

- 가장 큰 배움은 *측정 도구도 측정 대상이다*라는 것. 처음엔 부하 테스트 시나리오를 "사용자 행동을 모사하는 코드" 정도로 봤는데, 실제로는 그 시나리오의 sleep 길이·polling 횟수·재시도 정책 하나하나가 서버 부하 패턴을 결정한다. 시나리오 자체가 *조작 가능한 부하 생성기*다.
- Rate Limiter가 retry storm을 만들어낸 2회차 경험이 인상적이었다. *방어 메커니즘이 클라이언트 동작과 결합해 의도치 않은 양상을 만들 수 있다.* 실제 운영에서 클라이언트 retry 정책을 무방비로 풀면 정상 부하에서도 같은 일이 일어날 수 있다.
- 변곡점을 찾았다는 것보다, 변곡점을 찾기 위해 *두 개의 독립적 신호(k6 EOF + Grafana RPS 평탄화)가 같은 구간을 가리켜야 신뢰할 수 있다*는 검증 감각이 자리잡힌 게 더 가치 있었다. 하나만 봤으면 우연일 수 있다.

### 사례 3. nginx 튜닝이 답일 줄 알았다 — 가설이 뒤집힌 페일오버 실험

스케일아웃 효과는 Phase 4에서 확인했다. 그 다음 질문은 자연스러웠다 — *2대 중 1대가 죽으면 어떻게 되는가?* nginx의 `least_conn` + passive health check가 자동으로 격리해줄 것이다. 그런데 사용자에게 노출되는 에러는 얼마나 될까. 0에 가까울까, 아니면 의미 있게 발생할까. 직접 측정해보기 전에는 알 수 없는 영역이었다.

#### 베이스라인 — 30초 다운에 사용자 에러 20%

VU=800 정상 부하 중 T+150s에 앱 서버 1을 `docker kill`, T+180s에 `docker start`. 30초의 명시적 다운 윈도우. nginx 설정은 그대로 둔 상태(`max_fails=2`, `fail_timeout=10s`, `proxy_connect_timeout 5s`).

| 회차 | http_req_failed | http_req_duration max |
|---|---|---|
| 1 | 20.74% | 1m0s (k6 timeout) |
| 2 | 20.80% | 1m0s |

두 회차 에러율 차이가 0.06%p. 측정 노이즈가 아니라 *구조적 결과*라는 뜻이었다. nginx가 server1을 격리하기까지 약 10초 동안, 사용자 요청 일부는 죽은 서버로 라우팅되어 timeout 혹은 connection refused로 실패한다.

여기서 한 번 막혔다 — 이게 정상인가? *시스템 다운 없음 ✅, 사용자 에러 20% ⚠️* 이 두 결과를 어떻게 받아들여야 하는지 한참 생각했다. 합산 RPS 곡선은 끊기지 않았다. server2가 트래픽을 받아주고 있었다. 그런데 사용자 5명 중 1명이 에러를 봤다. 이게 *failover가 동작했다*인가, 아니면 *failover가 충분히 동작하지 못했다*인가.

passive health check의 본질을 다시 보고 답이 정리됐다. 이건 *사후 대응* 메커니즘이다. 진짜 요청이 실패해야 격리가 시작된다. 격리되기 전까지 들어온 요청은 반드시 죽은 서버로 간다. 즉 *수 %~수십 % 에러는 passive HC의 구조적 하한*이다.

#### 한 번 데인 일 — Prometheus가 server2를 모르고 있었다

베이스라인 1회차를 돌리고 Grafana를 봤는데, server1을 kill하는 순간 모든 패널이 공백으로 떨어졌다. 처음엔 nginx가 트래픽을 막은 줄 알았다. 시스템 전체가 멈춘 줄 알고 잠깐 멍해졌다.

이상한 점이 있었다. k6의 합산 RPS 곡선은 끊기지 않고 이어지고 있었다. server2가 어딘가에서 트래픽을 받고 있다는 신호였다. 그런데 Grafana 패널은 공백. 두 그래프의 비대칭이 단서가 됐다.

확인해보니 운영 서버의 `prometheus.yml` `scrape_configs`에 server1 IP만 등록되어 있었다. server1을 죽이니 Prometheus가 메트릭 수집을 잃었고, Grafana가 그릴 데이터가 없으니 패널이 공백으로 떨어진 것뿐이었다. server2는 멀쩡히 트래픽을 받고 있었지만 *측정되지 않았다*.

```yaml
# Before: server1만 등록
- targets: ['172.31.46.152:8080']

# After: server2 추가
- targets: ['172.31.46.152:8080', '172.31.37.7:8080']
```

수정 후 1회차를 폐기하고 베이스라인부터 다시 측정했다. 이 누락을 발견하지 못한 채로 진행했으면, 페일오버 분석에서 *server1이 죽은 30초 구간 — 가장 중요한 시간대* 의 메트릭이 통째로 비어 있는 그래프로 결론을 냈을 것이다.

추가로 패널 PromQL을 `sum(...)`에서 인스턴스별 분리(`{instance="..."}`)로 바꿨다. 합산 그래프로는 *어느 서버가 언제 끊기고 누가 트래픽을 받았는가*가 안 보인다. 두 인스턴스의 라인이 따로 그려져야 페일오버 동역학이 시각화된다. 이 두 작업 — 타겟 등록 보강 + 인스턴스별 패널 분리 — 이후로 측정 결과 자체가 분석할 만한 데이터로서 의미를 가지기 시작했다.

#### 첫 가설 — nginx를 더 공격적으로 튜닝하면 에러가 줄 것이다

baseline 20.77%를 줄여야 했다. 자연스러운 첫 가설은 *nginx가 죽은 서버를 더 빨리 격리하게 만들면 에러가 줄 것*이었다. 격리 속도를 결정하는 변수 세 개를 공격적으로 잡았다.

- `max_fails`: 2 → 1 (1번만 실패해도 격리)
- `fail_timeout`: 10s → 5s (격리 유지 시간 단축)
- `proxy_connect_timeout`: 5s → 1s (죽은 서버 응답 대기 시간 단축)

#### 실측 — 가설이 뒤집혔다

이 튜닝만 단독으로 적용해서 다시 돌렸다.

| 지표 | baseline (A) | nginx 튜닝 단독 (B) |
|---|---|---|
| http_req_failed | 20.77% | **24.51%** ⚠️ |
| 진입 성공률 | (미측정) | **5%** |

에러율이 줄긴커녕 *오히려 4%p 가까이 늘었다*. 진입 성공률은 5%로 폭락했다.

이 결과를 처음 봤을 때 결과를 의심했다. 측정 환경이 망가졌나, 시나리오가 잘못됐나. 다시 돌려도 비슷한 수치가 나왔다.

원인을 추적했다. `max_fails=1` + `connect_timeout=1s`가 *VU=800 정상 부하에서* false-positive 격리를 만들고 있었다. 정상 서버라도 한 순간 부하가 몰리면 1초 안에 connect 응답을 못 줄 수 있다. nginx는 그걸 "이 서버 죽었다"로 판정하고 격리한다. 트래픽이 다른 서버로 몰린다. 그 서버도 부하가 더 커져서 1초 응답을 못 한다. → 격리. *cascading isolation* 패턴이 만들어졌다.

이건 nginx.conf 주석에 "공격적 튜닝의 위험" 항목으로 미리 적어둔 트레이드오프였다. 이론적으로 알고 있었는데, 실측으로 확정된 게 처음이었다.

#### retry를 결합 — 이게 진짜 답이었다

같은 튜닝 + 클라이언트 retry(첫 실패 후 100ms 대기 → 재시도, 두 번째 실패 후 200ms 대기 → 재시도, 세 번째 실패 시 포기. 총 3번 시도)를 결합했다. 새 스크립트 `queue-flow-with-retry.js`를 따로 만들었다.

| 조건 | nginx 튜닝 | retry | http_req_failed | 진입 성공률 |
|---|---|---|---|---|
| A. baseline | OFF | OFF | 20.77% | — |
| B. 튜닝 단독 | ON | OFF | 24.51% ⚠️ | 5% |
| C. 결합 | ON | ON | **11.05%** ✅ | **38%** |

여기서 ablation의 진가가 드러났다. C가 baseline보다 좋아졌다는 사실(-47%)만 보면 *nginx 튜닝과 retry 둘 다 효과적이었다*라고 결론낼 뻔했다. 하지만 B(튜닝 단독)가 baseline보다 *나쁘다*는 사실이 같이 있으니 해석이 완전히 달라진다.

- nginx 튜닝 자체는 부작용이다 (A→B: +3.74%p)
- retry가 그 부작용을 *상쇄하고 추가로 개선*한다 (B→C: -13.46%p)
- 결합 효과의 *주역은 retry*이며, nginx 튜닝은 retry의 부작용을 흡수해주는 보조 역할

만약 ablation 없이 결합 효과만 봤으면 운영 가이드에 "nginx 튜닝값 max_fails=1·connect_timeout=1s를 적용하세요"라고 적었을 것이다. 그게 단독으로는 더 나쁜 설정이라는 사실을 모른 채.

#### 회고

- 이번 사례에서 가장 중요한 깨달음은 *그럴듯한 가설*과 *맞는 가설*의 거리다. "nginx를 공격적으로 튜닝하면 격리가 빨라지니 에러가 줄 것"은 들으면 누구나 끄덕일 가설이었다. 측정으로 확인하기 전까지는.
- ablation을 안 했으면 잘못된 운영 가이드를 만들 뻔했다. *변경 두 개를 동시에 적용하고 효과를 측정하는 것*과 *각각의 변경을 분리해서 측정하는 것*은 도출되는 결론이 다르다. 두 변수가 같은 방향으로 움직일 거라는 직관이 자주 틀린다.
- Prometheus 타겟 누락 일화에서 한 번 더 배웠다. *측정 인프라가 측정 대상의 가용성에 의존하면, 장애 상황에서 가장 필요한 순간에 데이터가 사라진다.* 이후로는 부하 테스트 전 체크리스트에 "Prometheus 타겟이 모든 인스턴스를 잡고 있는가" 항목이 들어갔다.
- 오픈소스 nginx + passive HC 단독으로는 *30초 다운 시 사용자 에러 ~20%가 구조적 하한*이라는 결론이 데이터로 확정됐다. 5% 미만 SLO를 잡으려면 active health check(K8s, 클라우드 LB, nginx-plus, nginx_upstream_check_module 중 하나)가 필수. 이건 측정 없이 "그냥 알아두는 것"과는 다른 무게의 결론이다.

### 사례 4. 100명이 동시에 같은 좌석을 잡으면 — 분산 락 불변식 증명

이 사례는 트러블슈팅이 아니라 *검증*에 가깝다. 시스템이 의도대로 동작하는지 부하 테스트로 통계적 증거를 모으는 작업이었다.

요구사항은 한 줄이었다. 앱 서버 2대 + nginx 환경에서 동일 좌석에 동시 선점 요청이 들어와도 *정확히 1명만 성공*해야 한다. 코드만 보고 "괜찮을 것이다"라고 결론내는 건 동시성 문제에서 가장 위험한 태도라고 봤다. 부하 테스트로 직접 통계를 모으기로 했다.

#### 설계

- Redis SETNX + UUID 토큰으로 좌석당 배타적 락. `ticketing.lock.ttl-seconds=3` — 정상 흐름이 1초 내 종료되는 것 기준 3배 여유. 보유자가 비정상 종료되어도 다음 요청이 빠르게 진입할 수 있다.
- Lua 스크립트로 unlock — `GET == 토큰 → DEL`을 원자로 처리. 다른 소유자의 락을 잘못 해제하는 사고를 막는다.
- Lua로 holdInfo 작성 — `EXISTS` 확인 → 좌석→토큰 SET → 토큰→상세 SET → 만료 ZADD를 한 번에. 중간에 끼어드는 연산이 없도록.
- Redisson을 도입하지 않았다. 단일 Redis 인스턴스에서 Redlock 알고리즘은 과한 복잡도라고 봤다. UUID 토큰 + Lua 해제로 동등한 안전성을 얻을 수 있다.

#### 검증 — k6 `shared-iterations` 100 VU × 100 iter, 단일 좌석, 각 구성 10회 반복

매 회차 전 `redis-cli FLUSHDB` + 좌석 DB 초기화(`status=AVAILABLE`, `seat_hold` 삭제). 1대 직접 구성과 2대 nginx 구성 각각 10회씩 총 20회 독립 시행.

| 응답 | 1대 직접 (10회 합) | 2대 nginx (10회 합) |
|---|---|---|
| **201 선점 성공** | 모든 회차 1건 | 모든 회차 1건 |
| 5xx | 0건 | 0건 |
| 409 이미 선점 | 0~7건 (회차별 변동) | 0~21건 (회차별 변동) |
| 429 락 경합 | 92~99건 (회차별 변동) | 78~99건 (회차별 변동) |

20회 독립 시행 전부 201이 정확히 1건. Redis가 단일 잠금 저장소이므로 요청이 nginx를 거쳐 2대에 분산되어도 락의 원자성이 유지된다는 사실을 통계적으로 확인했다. 409·429 비율은 회차마다 달라지지만, 두 응답 모두 중복 선점을 막는 올바른 동작이다 — 락 단계에서 걸리면 429, 락을 통과한 뒤 이미 선점 상태를 확인하면 409로 갈라질 뿐이다.

#### 부수 발견 — API 응답 코드 버그

부하 테스트는 정확성 검증으로 시작했는데 의외의 부산물이 따라왔다.

초기 검증에서 `201 선점 성공` 체크가 0건으로 나왔다. 그런데 `http_req_failed`를 역산하면 1건은 비실패였다. 추적해보니 `HoldController.createHold()`가 `ResponseEntity` 없이 `HoldResponse`를 직접 반환하고 있었고, Spring이 기본 200 OK를 적용한 결과였다. `@ResponseStatus(HttpStatus.CREATED)` 한 줄을 추가해 수정했다.

부하 테스트가 우연히 잡아낸 응답 코드 결함이었다. 통과/실패만 보지 않고 *응답 코드 분포까지 셈했기 때문에* 발견됐다.

#### 회고

- k6의 기본 동작은 4xx를 모두 실패로 집계한다. 이 시나리오에서는 409와 429가 정상 응답이므로 `http_req_failed: rate<1`로 임계값을 명시해 false alarm을 억제했다. 측정 도구의 디폴트가 도메인에 맞지 않으면 그 디폴트를 따져봐야 한다는 게 사례 2와 통하는 교훈이었다.
- 정확성 검증은 *한 번 통과했다*가 아니라 *20번 독립 시행 전부 통과했다*가 의미를 가진다. 단일 실행은 운으로 통과할 수 있다.

## 5. 구현 결정 사례

> 4장 트러블슈팅과 별개로, 정합성·보안 측면에서 신경 쓴 구현 결정 두 가지를 정리한다. 시스템의 안정성을 좌우하는 설계 선택이라 문서로 남긴다.

### 결제 — 외부 I/O가 끼인 트랜잭션을 어떻게 끊었나 (Saga 보상)

3단계 결제 플로우(READY → APPROVED → COMPLETED)의 마지막 단계에서 예약 확정(`reservationService.confirm()`)이 실패할 수 있다. 홀드 만료, 좌석 경합, DB 일시 장애 등. 이 시점에는 이미 포인트가 차감됐거나 카드 결제가 승인된 상태다. 그대로 두면 *돈은 빠졌는데 좌석은 없는 불일치*가 발생한다.

#### 단일 트랜잭션으로 묶는 게 답이 아닌 이유

`completePayment` 전체를 한 트랜잭션으로 묶으면 예외 시 롤백되어 깔끔할 것 같지만, 두 가지 이유로 안 된다.

- 결제 승인은 외부 PG(토스페이먼츠) HTTP 호출을 포함한다. 네트워크 시간이 트랜잭션 안에 들어가 락 보유 시간이 비현실적으로 길어진다.
- `users.point` 차감은 비관적 락이 필요하다. 좌석 락(Redis)과 트랜잭션 경계(DB)가 충돌한다.

트랜잭션 경계는 *비즈니스 흐름 단위*가 아니라 *정합성이 필요한 최소 단위*로 자르는 게 맞았다.

#### Saga 보상 트랜잭션 (REQUIRES_NEW)

- `PaymentCompensationService`를 별도 빈으로 분리하고 `@Transactional(propagation=REQUIRES_NEW)` 적용.
- 예약 확정 예외 발생 시 보상 메서드를 호출해 *포인트 환불 + Payment.status=CANCELED*를 독립 트랜잭션으로 커밋.
- 보상 후 원래 예외를 re-throw해 클라이언트에 정확한 오류 응답을 돌려준다.
- 좌석 락은 Redis 담당, 금전 정합성은 DB 비관적 락 담당으로 *역할 분리*.

별도 빈으로 분리한 이유는 self-invocation 회피다. 같은 클래스 내부 메서드 호출은 Spring AOP가 가로채지 못해 `REQUIRES_NEW`가 동작하지 않는다. Spring 트랜잭션에서 자주 빠지는 함정이라 따로 클래스로 빼는 게 안전했다.

#### 정합성 보장 포인트

| 시나리오 | 처리 |
|---|---|
| 예약 확정 중 예외 | REQUIRES_NEW 보상 → 포인트 환불 + CANCELED |
| 결제 API 중복 요청 | `Idempotency-Key` + Redis TTL + `@Idempotent` AOP |
| Reservation 커밋 후 Kafka 발행 실패 | Outbox PENDING 유지 → 스케줄러 재시도 (최대 25회) |
| Redis `releaseHold` 실패 | DB 예약은 커밋, Redis 홀드는 TTL까지 잔존 후 자동 만료 |

### JWT — 무상태성과 로그아웃 보안의 충돌을 어떻게 해결했나

JWT 인증을 도입할 때 두 가지 요구사항이 충돌했다.

1. **UX 측면**: Access TTL을 짧게 잡으면 사용자가 자주 재로그인해야 한다 → Refresh Token으로 자동 재발급이 필요하다.
2. **보안 측면**: JWT는 서명만 유효하면 만료 전까지 동작한다 → *로그아웃했는데도 탈취된 Access로 요청이 통과될 수 있다.*

#### Access + Refresh 두 토큰

| 항목 | Access | Refresh |
|---|---|---|
| TTL | 30분 | 14일 |
| 용도 | 매 요청 인증 | Access 만료 시 새 Access 발급 |
| 저장 | 클라이언트 `sessionStorage` | 클라이언트 `sessionStorage` + DB(`refresh_tokens`) |

매 요청에 Access + Refresh를 같이 보내고 만료 조합에 따라 4가지로 분기한다.

| 케이스 | Access | Refresh | 동작 |
|---|---|---|---|
| 1 | 만료 | 만료 | 401 → 재로그인 |
| 2 | 만료 | 유효 | 새 Access 발급 (`X-New-Access-Token` 헤더) |
| 3 | 유효 | 만료 | Access 살아있으니 정상 통과 |
| 4 | 유효 | 유효 | 정상 처리 |

별도 `/refresh` 엔드포인트 방식이면 클라이언트가 "401 받음 → refresh 호출 → 원래 요청 재시도" 3-step을 처리해야 한다. 두 토큰 동반 전송 방식은 *서버가 투명하게 재발급*해서 클라이언트 로직을 단순화한다. 트레이드오프는 요청마다 토큰 검증 비용이 두 번이라는 점이다.

#### 로그아웃 시 Access를 Redis 블랙리스트로 차단

- 로그아웃 시 Access의 jti(UUID)를 Redis에 블랙리스트로 등록(`jwt:bl:{jti}`).
- 매 요청에서 Access jti가 블랙리스트에 있는지 확인 → 있으면 401.
- TTL은 Access의 잔여 유효 시간만큼만 설정 → 만료되면 자동 삭제, Redis 메모리 낭비 없음.
- Refresh는 DB에서 `revoked = true` 마킹.

Access는 Redis, Refresh는 DB로 분리한 이유는 두 토큰의 수명·추적 요구가 달라서다. Access는 30분짜리라 TTL 기반 자동 만료가 자연스럽고 Redis가 적합하다. Refresh는 14일짜리 + 사용자별 토큰 추적이 필요하므로 DB가 적합하다.

#### 스케일아웃 환경에서의 무상태 인증

앱 서버가 2대로 늘어나도 JWT는 추가 작업 없이 동작한다.

- Access 검증은 서명 확인만으로 완결 → 서버 간 세션 공유가 불필요.
- 상태가 필요한 부분(블랙리스트, refresh DB)은 Redis와 MySQL을 공유 → 어느 서버로 라우팅돼도 동일한 결과.
- 새 서버를 추가해도 동일한 `JWT_SECRET`만 주입하면 즉시 동작.

"JWT는 무상태"라는 한 줄을 그대로 받아들이면 로그아웃 보안 구멍이 생긴다. *완전 무상태가 아니라, 무상태 + 최소한의 상태(블랙리스트, refresh DB) 조합*이 운영에 맞았다.

상세 설계는 [`jwt-auth.md`](jwt-auth.md)에 정리해뒀다.

## 6. 기술적 의사결정 (ADR)

#### ADR-1. Redis SETNX 분산 락 (Redisson 미사용)
- 단일 Redis 인스턴스에서 Redlock은 과도. UUID 토큰 + Lua 해제로 동등한 안전성 확보
- TTL 3초 — 정상 흐름(Redis 4회 + DB 1회)이 1초 내 종료되는 것 기준 3배 여유. 락 보유자가 비정상 종료되어도 다음 요청이 빠르게 진입
- Sentinel/Cluster 전환 시 라이브러리 재검토 필요 (현재 단일 인스턴스 전제)

#### ADR-2. Kafka 이벤트 드리븐
- 결제 알림(이메일/SMS) 외부 I/O를 결제 API 응답 시간에서 분리
- `acks=all`, `idempotence=true`, `retries=3`으로 유실 최소화
- `RESERVATION_CONFIRMED`는 Outbox로 DB 정합성 강화, DLT로 수동 재처리

#### ADR-3. DB 비관적 락 (결제·포인트)
- 금전 이중 차감 방지: `SELECT ... FOR UPDATE`
- 좌석 선점은 Redis 락, 결제 정합성은 DB 락 — **자원별 락 역할 분리**

#### ADR-4. 멱등성 키 (AOP)
- `Idempotency-Key` 헤더 + Redis TTL + `@Idempotent` AOP
- 컨트롤러 어노테이션 한 줄로 비즈니스 로직과 완전 분리

#### ADR-5. Java 21 Virtual Thread
- Tomcat 요청 스레드 VT 전환 → JVM live threads **225→30** (87% 감소)
- I/O 바운드 환경에서만 효과 — DB 쿼리 빈도가 병목이면 처리량 개선은 제한적 (사례 1 참조)
- 제외 영역: 스케줄러 트리거, Netty/Kafka Producer 내부

#### ADR-6. SSE 다중 인스턴스 — Redis Pub/Sub 브로드캐스트
- 문제: Kafka 컨슈머가 어느 앱 인스턴스에서 실행되는지 제어 불가 → 사용자가 app1에 SSE 연결됐는데 app2가 알림 발행하면 누락
- 대안 비교:
  - **스티키 세션(`ip_hash`)** — 같은 사용자를 같은 앱으로 라우팅하지만 **Kafka 컨슈머 실행 인스턴스는 독립** → 본질 해결 안 됨
  - **클라이언트 폴링** — 푸시 모델의 즉시성 포기
  - **Redis Pub/Sub** ✅ — 발행은 어느 인스턴스든, 구독은 모든 인스턴스. 자기 emitter 보유분만 send
- 구현: `SseNotificationService implements MessageListener` + `SseRedisConfig`의 `RedisMessageListenerContainer`가 `sse:notify:*` PSUBSCRIBE
- 검증: `SseNotificationMultiInstanceIntegrationTest` (Testcontainers Redis) 4 시나리오 — cross-instance broadcast / 양쪽 동시 연결 / 사용자 격리 / no-op
- 트레이드오프: SSE 연결 자체는 인스턴스 로컬 유지(연결 메타까지 Redis로 올리면 과한 설계). 배포 중 끊김은 클라이언트 재연결 + Redis List `notify:user:{userId}` 폴링으로 보완

| 1대, pool=30 + VT | 800 | 2.06s | 376/s | 0% |
| **1대, pool=30 + VT + 잔여석 캐시** | 800 | **444ms** | **834/s** | **0%** |
| **2대, nginx + 동일 구성** | 800 | **164ms** | **1,447/s** | **0%** |
| 2대, VU=1500 (한계 부하) | 1500 | 1.74s | 1,177/s | 3.41% |
| 동시 선점 정확성 (VU=100, 20회 시행) | - | - | - | 201: **모든 회차 1건** |
| **2대, app1 30s 다운 (페일오버)** | 800 | 246ms | - | **20.77%** |
| 2대, 페일오버 + nginx 튜닝 + 클라이언트 retry | 800 | 180ms | - | **11.05%** |

> 페일오버 에러율 ~20%는 nginx passive health check(`max_fails=2 fail_timeout=10s`)의 구조적 결과 — kill 후 ~10초 격리 지연 동안 사용자 에러 발생. 두 회차 0.06%p 차이로 재현.
>
> **개선 시도 (ablation)**: nginx 튜닝(`max_fails=1`·`connect_timeout=1s`) + 클라이언트 retry 결합으로 **20.77% → 11.05% (-47%)**. 단, ablation 측정으로 **nginx 튜닝 단독은 false-positive 격리로 오히려 24.51%로 악화**, 클라이언트 retry가 개선의 주역임을 확인. 운영 SLO 5% 미만은 active HC 도입 필수.

**전체 분석**: [`load-test-portfolio.md`](load-test-portfolio.md)

## 9. 프로젝트 구조

```
src/main/java/com/inyoung/ticketing/
├── auth/          # JWT 인증 (Access 블랙리스트 + Refresh jti revoke)
├── concert/       # 콘서트 도메인
├── seat/          # 좌석 도메인 (AVAILABLE / HOLD / RESERVED)
├── hold/          # 좌석 선점 (Redis Lua 원자 연산)
├── queue/         # 대기열 (Redis ZSet)
├── reservation/   # 예약 확정 (DB 트랜잭션 + Outbox)
├── payment/       # 결제 (READY→APPROVED→COMPLETED, Saga 보상)
├── notification/  # Kafka→이메일/SMS/SSE
├── outbox/        # Transactional Outbox
├── lock/          # Redis 분산 락 (SETNX + Lua unlock)
├── scheduler/     # 5종 배치 (분산 락 적용)
├── metrics/       # Prometheus 커스텀 메트릭
├── common/        # AOP (멱등성·Rate Limit), 예외 처리
└── config/        # Security, Redis, Kafka, Resilience4j
```
