# 부하 테스트 결과 비교 (loadtest-compare)

서로 다른 조건의 측정 결과를 비교해 **무엇이 성능 변화를 일으켰는지** 가린다.
티켓팅 프로젝트에서 자주 하는 작업: 캐시 전/후, poolsize 변경, Virtual Thread
on/off, nginx 튜닝, retry 도입 등의 효과를 분리(ablation)해서 본다.

## 입력 (2개 이상)

각 비교군마다 아래 중 하나:
- `loadtest-harness/reports/<...>/report.md`
- raw k6 summary JSON / k6 콘솔 출력
- Grafana 수치 / 수기 메모

각 비교군의 **설정 차이(변경된 변수)**를 먼저 명확히 식별한다. 무엇이 바뀌었는지
모르면 비교 의미가 없으므로 사용자에게 확인한다.

## 절차

1. **비교군 정렬**: 각 군의 핵심 지표(평균 RPS, p95/max 지연, 실패율, 서버측
   병목 지표)를 같은 표에 나란히 놓는다. baseline을 명시한다.
2. **델타 계산**: baseline 대비 증감(절대값 + %)을 표기한다.
3. **변경 변수 매핑**: 각 비교군에서 바뀐 변수를 명시한다(예: poolsize 10→30,
   캐시 미적용→적용). **변수가 동시에 여러 개 바뀌었으면 단일 귀속 불가**임을
   분명히 경고한다.
4. **주역 판정**: 가장 큰 개선/악화를 만든 변경을 지목하되, **근거 지표와 함께**
   제시한다. 교란요인(워밍업 차이, 측정 시점, 부하 패턴)이 있으면 명시한다.
5. **결론**: "X 단독으로는 효과 미미/악화, 실제 개선은 Y가 주역" 같은 ablation
   문장으로 정리한다(과거 nginx 튜닝 vs retry 분석과 동일한 틀).

## 정직성 원칙 (반드시 준수)

- 여러 변수가 한꺼번에 바뀐 비교는 **단일 원인으로 단정하지 않는다.**
- 개선/악화 주장은 항상 **수치 델타와 근거 지표**를 동반한다.
- 회차 편차가 큰데 평균만으로 우열을 가리지 않는다(표준편차/회차수 고려).
- 교란요인이 있으면 결론 전에 명시한다. 좋아 보이게 포장하지 않는다.

## 출력 형식

```
## 비교 대상 (변경 변수)
(군별 설정 차이)

## 지표 비교 표
| 지표 | A(baseline) | B | 델타(%) | ... |

## 주역 판정
(근거 지표 인용 + ablation 문장)

## 교란요인 / 한계

## 결론
```
