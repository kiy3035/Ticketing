# 변경점 커밋 + PR 자동화 (commit)

작업 단위가 끝나면 **확인을 묻지 않고** 커밋 → push → main 대상 PR 생성까지 자동으로 하고,
사용자에게는 PR 요약만 제시한다. 사용자는 PR을 보고 머지(수락)만 하면 된다.

## 자동화 규칙 (이 프로젝트 합의사항)
- **묻지 않는다.** "커밋할까요?" "PR 만들까요?" 식 확인 없이 바로 진행한다.
- **PR base는 항상 `main`.** 작업은 `main`에서 분기한 새 브랜치에서 한다(스택 금지).
- **머지는 사용자가 한다.** 절대 자동 머지하지 않는다. 브랜치는 머지 시 자동 삭제됨(레포 설정).
- 단, 비밀값이 섞였거나 변경이 위험하면 멈추고 알린다(아래 안전 점검).

## 절차

1. **변경 파악**
   - `git status --short`, `git diff`(staged+unstaged), `git diff --stat` 확인.
   - `git log --oneline -10` 으로 이 레포의 커밋 메시지 스타일을 참고한다.
   - 실제 diff를 **반드시 눈으로 확인**한다. 설명과 다른 변경이 섞여 있으면 알린다.

2. **안전 점검**
   - 비밀키/토큰/`.env`/PEM/자격증명 류가 staged에 섞였으면 **경고하고 제외**를 제안한다.
   - 생성물·대용량 바이너리·`.venv`/`__pycache__` 등이 들어갔으면 `.gitignore` 보강 제안.

3. **브랜치 확인**
   - 새 작업이면 **`main`에서 분기한 새 브랜치**를 만든다. 변경 요지로 이름 지정
     (예: `feat/...`, `fix/...`, `docs/...`). 다른 feature 브랜치 위에 스택하지 않는다.
   - 이미 해당 작업의 브랜치에서 진행 중이면 그대로 사용한다.

4. **커밋 그룹핑 판단**
   - 논리적으로 한 커밋이 적절한지 본다. 성격이 다른 변경이 크게 섞였으면
     분할 커밋을 제안한다(사용자가 한 번에 원하면 한 커밋으로).

5. **커밋 메시지 생성**
   - 제목: 간결한 한 줄. **이 레포는 한국어 제목 사용** → 한국어로, 변경 성격이
     드러나게(무엇을 했는지). 예: `부하 테스트 자동화 하네스 추가`.
   - 본문(필요 시): 무엇을/왜. 매직값 외부화·테스트 추가 등 핵심 포인트.
   - 메시지 끝에 트레일러 추가:
     ```
     Co-Authored-By: Claude Opus 4.8 <noreply@anthropic.com>
     ```

6. **스테이징 + 커밋 + push + PR (자동, 묻지 않음)**
   - 의도한 파일만 stage 후 commit.
   - `git push -u origin <branch>` 로 push.
   - `gh pr create --base main` 으로 **main 대상 PR 자동 생성**. 본문은 아래 PR 본문 템플릿을 따른다.
   - **자동 머지하지 않는다.** 머지는 사용자 몫(머지 시 head 브랜치는 레포 설정으로 자동 삭제).

7. **PR 본문 템플릿 (면접관도 읽는다는 전제 — 과장·허위 없이, 가독성 우선)**
   ```markdown
   ## 무엇을 / 왜
   (1~3줄: 이 PR이 하는 일과 이유)

   ## 변경 전 → 후 (Before → After)
   - Before: (기존 동작/구조/문제)
   - After: (바뀐 동작/구조)

   ## 기술·접근 선택과 트레이드오프
   - 고민한 점: (무엇을 결정해야 했나)
   - 선택: (무엇을 골랐고 왜)
   - 대안과 기각 이유: (검토한 다른 방법 — 있을 때만)
   - 트레이드오프: (얻은 것 ↔ 포기/감수한 것 — 솔직하게)

   ## 검증 / 테스트 상태
   (추가/통과/미실행을 사실대로. 미검증은 미검증이라고 명시)

   ## 리스크 · 리뷰 포인트
   (깨질 수 있는 곳, 리뷰어가 집중해서 볼 부분)

   🤖 Generated with [Claude Code](https://claude.com/claude-code)
   ```
   - **적응적으로 작성.** 사소한 변경이면 "기술·선택/트레이드오프" 섹션은 한 줄이거나 생략 가능.
     단 **Before→After와 검증 상태는 항상** 포함한다.
   - **과장·허위 금지.** 측정 안 한 성능 수치, 안 돌린 테스트를 통과한 것처럼 쓰지 않는다.
     불확실하면 불확실하다고 쓴다. 트레이드오프의 '나쁜 쪽'도 숨기지 않는다.
   - 커밋·PR 생성 후, 사용자에게는 이 본문을 짧게 요약해 PR 링크와 함께 제시한다.

## 정직성 원칙

- 테스트가 실패했거나 안 돌렸으면 그대로 보고한다. 통과한 것처럼 쓰지 않는다.
- 커밋 메시지가 실제 diff와 일치하는지 확인한다. 과장하지 않는다.
- 되돌리기 어렵거나 외부로 나가는 동작(push, PR, force)은 먼저 확인한다.
- 훅(hook)·서명을 임의로 건너뛰지 않는다(`--no-verify` 등 금지, 사용자가 요청하지 않는 한).

## 참고

- 더 깊은 코드 리뷰가 필요하면 `/code-review`, 변경 검증은 `/verify` 안내.
